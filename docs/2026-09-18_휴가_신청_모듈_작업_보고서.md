# 휴가 신청 모듈 작업 보고서

- 작업일: 2026-09-18
- 작업 범위: 휴가 신청·승인 모듈 백엔드 및 React 연동
- 참고 문서: Notion ERP 프로젝트의 모듈화 전략, 비즈니스 규칙 명세, 기능 명세,
  핵심 기능 상세 명세, 휴가 승인자 결정·상태 전이 문서

## 1. 작업 개요

Notion에서 정의한 DDD + 클린 아키텍처 모듈화 규칙에 따라 휴가 신청 모듈을 구현했다.
휴가 도메인은 Django 앱 하나로 구성하되 내부를 Domain, Application, Infrastructure,
Presentation 레이어로 분리했다.

현재 저장소에는 사원·조직·역할·인증 및 휴가 잔여일수 모듈이 없으므로 계약 우선 방식으로
구현했다. 휴가 모듈은 해당 기능을 추상 포트로만 참조하며, 현재 시연에는 설정 기반 개발용
어댑터를 사용한다.

## 2. 적용한 아키텍처

### Domain

- Django 및 DB 의존성이 없는 순수 Python 코드로 구성
- 휴가 신청, 휴가 유형, 상태 이력 엔티티 구현
- 휴가 기간과 차감일수 값 객체 구현
- `대기`, `승인`, `반려`, `취소`, `회수` 상태 정의
- 승인, 반려, 취소, 승인 회수, 수정·재신청 상태 전이 규칙 구현
- 신청자와 승인자 권한 검증 및 잘못된 상태 전이 차단
- Repository 및 Unit of Work 추상 인터페이스 정의

### Application

- 휴가 신청·조회·취소·승인·반려·회수·재신청·이력 조회 유스케이스 구현
- 재직 여부, 승인자 결정, 잔여일수 조회를 외부 포트로 분리
- 신청 및 재신청 시 잔여일수 검증
- 상태 변경과 상태 이력 기록을 하나의 Unit of Work로 처리
- API 계층과 독립적인 입력 DTO 및 응답 변환 함수 제공

### Infrastructure

- Django ORM 모델과 Domain 엔티티를 별도로 정의
- ORM 모델과 Domain 엔티티 간 Mapper 구현
- Django Repository 및 트랜잭션 기반 Unit of Work 구현
- `leave_types`, `leave_requests`, `leave_request_history` 테이블 migration 생성
- 연차, 반차, 병가 기본 휴가 유형을 migration 초기 데이터로 추가
- 인덱스와 기간·차감일수 CHECK 제약 추가
- 설정 기반 개발용 사원·승인선·잔여일수 어댑터 구현

### Presentation

- Django REST Framework 기반 API 구현
- Serializer는 요청 형식 검증만 담당하도록 제한
- View는 유스케이스 조립, 호출 및 HTTP 응답 변환만 담당
- React에서 신청자·승인자 역할을 전환하며 전체 흐름을 확인할 수 있도록 연결

## 3. 구현 기능

Notion 기능 명세의 휴가 기능을 다음과 같이 반영했다.

1. `FN-LV-001` 휴가 신청
2. `FN-LV-002` 본인 휴가 신청내역 조회
3. `FN-LV-003` 대기 휴가 신청 취소
4. `FN-LV-004` 승인대상 휴가 조회
5. `FN-LV-005` 휴가 승인·반려
6. `FN-LV-006` 승인 휴가 회수
7. `FN-LV-007` 회수된 휴가 수정·재신청
8. `FN-LV-008` 휴가 정정 이력 조회

## 4. API

모든 엔드포인트는 `/api/vacations/` 아래에 구성했다.

- `GET types/`: 휴가 유형 목록
- `GET requests/`: 본인 휴가 신청 목록
- `POST requests/`: 휴가 신청
- `GET approvals/`: 현재 사용자의 승인 대상 목록
- `POST requests/{id}/cancel/`: 대기 신청 취소
- `POST requests/{id}/approve/`: 휴가 승인
- `POST requests/{id}/reject/`: 휴가 반려
- `POST requests/{id}/recall/`: 승인 휴가 회수
- `PUT requests/{id}/resubmit/`: 회수된 휴가 수정·재신청
- `GET requests/{id}/history/`: 휴가 상태 변경 이력

현재 개발용 사용자 식별은 `X-Employee-No` 헤더를 사용한다. 이는 인증 구현이 아니며 운영
환경에서는 Django 인증 사용자와 사원번호를 연결하는 실제 어댑터로 반드시 교체해야 한다.

- 대기 신청 취소
- 승인·반려
- 승인 회수
- 회수된 신청 수정·재신청

- 데스크톱과 모바일 레이아웃 대응

## 6. 테스트 및 검증

공유 PostgreSQL에는 migration을 적용하지 않았다. API 통합 테스트는 인메모리 SQLite 전용
설정을 사용해 공유 데이터에 영향을 주지 않도록 했다.

실행 결과:

- Ruff 검사 통과
- 순수 Domain 및 Application 테스트 통과
- migration을 포함한 DRF 신청 → 승인 → 이력 조회 통합 테스트 통과
- 전체 테스트 6개 통과
- Django system check 통과
- migration 변경 누락 검사 통과
- Frontend ESLint 통과
- Frontend TypeScript 및 Vite production build 통과

### 로컬 시연 확인

- 공유 PostgreSQL 대신 파일 기반 SQLite를 사용하는 `config.demo_settings` 추가
- Django 백엔드 `localhost:8000`, Vite 프론트엔드 `localhost:5173` 실행 확인
- 브라우저에서 사원 1001의 휴가 신청 생성 후 승인자 2001로 전환해 승인 처리 확인
- 승인 완료 메시지와 승인 회수 액션 노출 확인
- 외부 웹폰트 의존성을 제거해 네트워크가 제한된 환경에서도 시스템 글꼴로 표시

4. 대상 환경과 DB 권한을 확인한 후 migration 적용
5. 운영 인증·권한 테스트 및 PostgreSQL 통합 테스트 추가
6. 필요 시 휴가 기간 중복, 휴일 계산, 반차 시간 정책 등 후속 업무 규칙 확정

## 9. 주의사항

- 승인된 휴가는 직접 수정할 수 없으며 반드시 `승인 → 회수 → 대기 → 승인/반려` 흐름을
  거친다.
- 상태 변경과 이력 생성은 동일한 트랜잭션으로 처리한다.
- 개발용 사원번호 헤더는 누구나 위조할 수 있으므로 운영 환경에서 사용할 수 없다.
- 공유 DB에는 명시적인 환경·권한 확인 없이 migration 또는 데이터 쓰기 작업을 실행하지 않는다.
