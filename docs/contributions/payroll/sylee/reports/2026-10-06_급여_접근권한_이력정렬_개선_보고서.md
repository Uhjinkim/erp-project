# 급여 모듈 접근 권한·이력 정렬 개선 보고서

- 작업일: 2026-10-06
- 작업 범위: 급여 모듈 백엔드 접근 권한 보강(본인 초안 비노출, 급여담당자 자기거래
  방지), 급여 변경 이력 정렬 순서 변경
- 참고: `2026-09-23_급여_UI_개선_보고서.md` 이후 작업이다. 사용자가 전달한 피드백
  메모(수정 필요 사항·고민하고 있는 부분)와 별도 요청 1건을 반영했다.

## 1. 요청 사항

사용자가 전달한 메모는 세 부분으로 구성되어 있었다.

1. **수정 필요 사항**: 급여담당자가 작성중(미확정) 상태로 만들어 둔 급여를 해당
   사원이 본인 급여 페이지에서 미리 볼 수 있는 문제 — 확정된 뒤에만 노출되도록
   수정 필요.
2. **고민하고 있는 부분**(미확정, 질문으로 확인):
   - 특수 상황을 위한 추가 입력 필드(상여 등)를 계속 고정 목록으로 관리할지, 화면에서
     직접 새 항목을 만들 수 있게 할지.
   - 급여담당자가 한 명이 아니므로, 본인 급여는 본인이 입력하지 못하게 막을지.
3. **별도 요청**: 급여 변경 이력을 오래된 순이 아니라 최신순(가장 최근 처리가 맨
   위)으로 정렬.

"고민하고 있는 부분"은 결정되지 않은 사항이라 임의로 구현하지 않고 먼저 질문했다.
답변은 다음과 같았다.

- 추가 구성항목: 지금처럼 고정 목록 + 필요할 때 migration으로 추가하는 방식을
  유지하되, 미리 예상되는 항목을 선제적으로 넣지 말고 정말 필요한 것만 추가한다.
- 급여담당자 본인 급여: 본인은 입력·수정·확정할 수 없게 막는다(다른 급여담당자가
  처리).

## 2. 반영 내용

### 2.1 본인 급여는 확정된 것만 노출

`PayrollService.list_mine()`은 이제 `확정` 상태인 급여만 반환한다. `get()`/
`history()`도 본인이 조회하는 경우 `확정` 상태가 아니면 `PayrollPermissionError`
(403)를 발생시킨다. 단, 급여담당자가 관리 화면에서 보는 경로(`list_for_employee`,
`list_all`)는 이 제한을 적용하지 않는다 — 작성중 상태를 봐야 편집·확정할 수 있기
때문이다. 즉 "본인 조회" 경로에만 확정 여부 제한을 걸고, "관리자 조회" 경로는
그대로 둔다.

### 2.2 급여담당자 본인 급여 자기거래 방지

`PayrollService._require_not_self()`를 추가해 `create_statement`,
`update_items`, `confirm`, `cancel_confirmation` 네 곳 모두에서 처리자(`actor`)와
대상 사원이 같으면 거부하도록 했다. 조회는 막지 않는다 — 급여담당자가 본인 급여를
관리 화면에서 확인하는 것 자체는 허용하고, 입력·수정·확정·확정취소만 다른
급여담당자가 하도록 제한했다.

### 2.3 이력 최신순 정렬

`DjangoPayrollHistoryRepository.list_for_statement()`가 `-changed_at,
-history_id` 순으로 정렬해 반환하도록 변경했다. 프론트엔드는 받은 순서 그대로
렌더링하므로 별도 수정이 필요 없었다.

## 3. 변경 파일

- `payroll/application/service.py`: `list_mine()` 확정 필터, `get()`/`history()`의
  `_require_visible_to_requester()`(기존 `_require_owner_or_manager()`를 대체),
  `_require_not_self()` 및 4개 유스케이스에 적용
- `payroll/infrastructure/repositories.py`: 이력 조회 정렬 순서 변경
- `tests/test_payroll_service.py`, `tests/test_payroll_api.py`: 위 변경에 맞춰
  기존 테스트 수정, 자기거래 방지·초안 비노출·이력 정렬에 대한 테스트 추가
- `docs/specs/notion/payroll-implementation-map.md`: 변경 사항 반영

## 5. 참고

"특수 상황 추가 입력 필드"는 이번에 코드를 바꾸지 않았다 — 담당자가 선제적으로
항목을 늘리지 않기로 결정했으므로, 실제로 필요한 항목이 생기면 그때 요청해 달라고
안내했다.
