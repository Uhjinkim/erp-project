## 작성 결과

저장소의 Graphite 와이어프레임 39장과 현재 App·모듈 Panel·API·전송 타입·의존성 구성을 확인했다.
공통 토대 F0와 홈·본인 정보·사원 조직·휴가·게시판·평가·급여·시스템 F1~F8을 나누고, 모든 화면 ID에
단일 담당 단위를 지정했다. 업무 흐름은 모듈 내부에 묶고 공용 파일은 F0가 소유하도록 계획했다.

디자인시스템에 포함할 기본 UI와 조건부 복합 패턴, 앱 공통과 모듈 전용 항목을 구분했다.
기존 workforce API·타입 분할, App의 휴가 이관, CSS 범위와 공용 변경 요청 절차를 기록했다.
분석→계약→토대→대표 흐름→모듈 병렬 구현→통합 검수 순서와 단계별 완료 조건을 작성했다.

안내서는 후속 구현 목표다. 이번 작업에서 앱 코드·의존성·API·스키마·업무 규칙은 변경하지 않았다.
제품 명세 변경이 없어 specs 스냅샷은 유지하고 루트 README에 안내서 진입 링크를 추가했다.

## 남은 확인 사항

- 디자인 기준 확인 질문 도구가 응답 없이 시간 초과되었다. Graphite는 화면 분할 참고 기준으로만
  기록했으며 사용자 확인으로 확정된 시안이라고 주장하지 않는다. 실제 확정 시안·버전과 착수 전 대조한다.
- 담당자 실명·일정·모바일 범위·폰트·도구·공통 계약의 최종값은 토대 작업 카드에서 정한다.
- 기존 INT-01·HR·BD·EV·PY·OPS 의제는 현재 코드로 재확인하며 이번 안내서에서 해결 완료로 처리하지 않았다.
- Notion 원문 재조회·수정, 팀원 메시지 전송, 공유 DB·Redis 접속·변경은 수행하지 않았다.

## 검증

- README·안내서·작성 기록의 상대 링크와 Markdown 코드 블록 검사 통과.
- 와이어프레임의 39개 화면 ID가 배정표에 각각 한 번씩 포함되는지 검사 통과.
- `git diff --check`와 새 문서의 공백 검사 통과. 최종 diff/status를 확인했다.
- 문서만 변경하여 프론트 lint/build·백엔드 검증·브라우저 동작 검증은 실행하지 않는다.
  실제 토대·모듈 구현 시 수행할 검증은 안내서에 명시했다.
- dev의 사용자 요청 공용 문서 작업이므로 기능 브랜치 문서 범위 검사는 적용하지 않는다.
- 기존 휴가 검토 보고서의 사용자 변경은 수정하지 않는다.
