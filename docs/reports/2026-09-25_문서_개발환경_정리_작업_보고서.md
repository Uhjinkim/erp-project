상태 확인, 세션 인증, 계정, 사원·조직·역할, 휴가 API의 요청·응답, 검증, 오류와 상태 전이를
문서화했다.

- 저장소 명세: `docs/specs/notion/06-api-specification.md`
- Notion 원문: `06. API 명세`
- 설계 명세 목차의 `01`~`05` 다음에 `06`으로 배치
- Notion 표는 네이티브 표 블록으로 변환해 전체 내용을 반영

## 2. 테이블 설계 문서 정리

- `07-table-design-decisions.md`: Notion `07. 테이블 설계 결정안`의 구현 관점 스냅샷

Notion과 저장소 문서에는 계정번호, 사원 개인정보, 인증정보와 실제 환경변수 값을 기록하지 않았다.

## 4. nginx 설치 안내

README에 플랫폼별 nginx 설치 안내를 추가했다.

- macOS: Homebrew 설치 명령
- Ubuntu/Debian: 배포판 패키지 설치 명령
- Windows: `winget install nginxinc.nginx` 실행, 새 PowerShell 시작과 `nginx -v` 확인

Windows에서 설치한 개발용 nginx는 서비스로 등록하지 않고 통합 스크립트가 콘솔 프로세스로
관리한다.

## 5. Windows nginx 임시 디렉터리 처리

`scripts/start-dev.ps1`은 실행별 임시 nginx prefix를 사용하지만, Windows nginx가 요청 본문과
프록시 버퍼링에 사용하는 하위 디렉터리를 만들지 않았다. 설치 형태와 요청에 따라 임시 경로 생성
오류가 발생할 수 있어 설정 검사 전에 다음 디렉터리를 자동 생성하도록 수정했다.

- `logs`
- `client_body_temp`
- `proxy_temp`
- `fastcgi_temp`
- `uwsgi_temp`
- `scgi_temp`

이 디렉터리는 OS 임시 경로 아래의 실행별 디렉터리에 생성되며 스크립트 종료 시 기존 정리 로직으로
함께 삭제된다. nginx가 설치되지 않았을 때의 오류 메시지에도 WinGet 설치 명령과 새 PowerShell
세션을 열어야 한다는 안내를 포함했다.

## 6. 검증

- Django test settings 시스템 검사 통과
- `bash -n scripts/start-dev.sh` 통과
- 공통 nginx 개발 설정 검사 수행
- Notion 목차의 `06 → 07 → 08` 순서와 각 문서 내용 재조회 확인
- Markdown 후행 공백과 `git diff --check` 검사 통과

현재 작업 환경에는 PowerShell 실행기가 없어 `start-dev.ps1 -Check`를 직접 실행하지 못했다.
PowerShell 문법과 경로 생성·정리 흐름은 정적으로 검토했으며, 최종 Windows 확인은 nginx를 설치한
Windows PowerShell에서 다음 명령으로 수행한다.

```powershell
.\scripts\start-dev.ps1 -Check
```

공유 데이터베이스 migration, seed, 데이터 변경 또는 Redis 쓰기·초기화는 수행하지 않았다.

## 7. 기능 브랜치·문서 협업 워크플로우

기능 모듈을 별도 브랜치에서 병렬 개발하면서 공용 문서 충돌을 줄이는 협업 규칙과 스크립트를
추가했다.

- `dev`: 기능과 공용 문서의 통합 기준 브랜치
- `main`: 검증된 `dev`를 반영하는 릴리스 브랜치
- 기능 브랜치: 모듈 코드와 `docs/contributions/<module>/<branch-slug>/` 기여 문서만 변경
- 문서 담당자: Notion 원문과 저장소 공용 문서를 `dev`에서 통합

`scripts/docs-workflow.sh`와 `scripts/docs-workflow.ps1`은 다음 명령을 제공한다.

- `init <module>`: 현재 브랜치 전용 기여 문서 템플릿 생성
- `sync`: `origin/dev`의 공용 문서만 동기화하고 기능 브랜치 기여 문서는 보존
- `check`: Pull Request 전 기능 브랜치의 공용 문서 직접 변경 여부 검사

전체 코드 통합 상태를 확인하려면 정기적으로 `origin/dev`를 기능 브랜치에 merge하고, 문서 전용
동기화는 코드 병합 시점을 늦춰야 할 때만 사용한다. 세부 절차는
`docs/guides/module-branch-docs-workflow.md`에 기록했다.

격리된 임시 Git 원격과 `dev`, 기능 브랜치를 생성해 `init → dev 문서 변경 → sync → check` 흐름을
검증했다. 기여 초안 보존과 공용 문서 동기화가 정상 동작했으며, 기능 브랜치에서 공용 README를
임의 수정한 경우 `check`가 실패하는 것도 확인했다.

## 8. 에이전트 공통 작업 규칙

Codex, Claude와 다른 코딩 에이전트가 동일한 아키텍처와 협업 절차를 따르도록 루트 `AGENTS.md`를
갱신했다.

- `AGENTS.md`를 단일 규칙 원문으로 지정하고 `CLAUDE.md`는 해당 문서를 읽도록 연결
- `dev` 통합, `main` 릴리스와 기능 브랜치 문서 소유권 명시
- Backend 4계층과 cross-context port/gateway 경계 강화
- 신규 모듈 구현 순서와 에이전트 완료 체크리스트 추가
- Notion 쓰기 권한이 없는 팀원·에이전트의 변경 제안 절차 명시
- API·테이블 정본과 기능 브랜치 기여 초안의 역할 구분

에이전트별 규칙 파일에 같은 내용을 복제하지 않고 `AGENTS.md`를 참조하게 해 도구별 지침이 시간이
지나며 달라지는 문제를 방지했다.
