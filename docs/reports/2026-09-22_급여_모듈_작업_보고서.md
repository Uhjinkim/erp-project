# 급여 모듈 작업 보고서

- 작업일: 2026-09-22
- 작업 범위: 급여 정산 모듈 백엔드(Django) 및 React 연동
- 참고 문서: Notion ERP 프로젝트의 모듈화 전략, 개요·Actor·상태, 비즈니스 규칙,
  기능 명세, 핵심 기능 상세 명세, 미확정 정책 문서 및 급여 모듈 담당자가 직접
  전달한 Notion 원문 파일(`PY-001`~`PY-009`, `FN-PY-001`~`FN-PY-007`)

## 1. 작업 개요

Notion에서 정의한 DDD + 클린 아키텍처 모듈화 규칙에 따라 급여 정산 모듈을 새 Django
app(`payroll`)으로 구현했다. `vacation`, `workforce`와 동일하게 내부를 Domain,
Application, Infrastructure, Presentation 네 계층으로 분리했다.

작업 착수 시점에 저장소의 Notion 스냅샷(`docs/specs/notion/`)에는 급여 규칙이 한 줄
요약만 있었고, Notion MCP 커넥터도 이 세션에서는 인증되지 않아 원문을 직접 조회할 수
없었다. 이에 따라 먼저 사용자에게 (1) 상세 규칙 확보 방법, (2) 급여 구성항목 범위,
(3) 정산일자 정책, (4) 이번 작업 범위를 확인했다. 사용자가 Notion 원문 파일을 직접
전달했고, 정산일자는 "매월 25일(휴일·공휴일이면 직전 평일)"로 이 세션에서 확정했으며,
급여 구성항목은 기본급+고정수당·초과근무수당 등 변동수당·4대보험 공제로 범위를
지정했다. 작업 범위는 백엔드와 프론트엔드 모두로 확인했다.

## 2. 적용한 아키텍처

### Domain

- Django 및 DB 의존성이 없는 순수 Python 코드로 구성
- `PayrollStatement`(급여 정산), `PayrollItem`(구성항목), `PayrollHistory`(이력),
  `PayrollComponentType`(구성항목 마스터) 엔티티 구현
- 정산월(`PayPeriod`) 값 객체 구현, `작성중`/`확정` 상태와 확정·확정취소 전이 규칙 구현
- 확정 상태에서는 구성항목을 직접 수정할 수 없도록 차단(`PY-005`)하고, 확정취소에는
  사유를 필수로 요구(`PY-006`)
- 원 단위 미만 금액을 최종 지급액 산정 시에만 올림 처리하는 정책 함수 구현(`PY-009`)
- 정산일자를 "매월 25일, 휴일/공휴일이면 직전 평일"로 계산하는 정책 함수 구현
- Repository 및 Unit of Work 추상 인터페이스 정의

### Application

- 급여 생성·구성항목 입력수정·확정·확정취소·조회·이력 조회 유스케이스 구현
- 사원 존재 여부, 급여담당자 권한 확인을 외부 포트로 분리해 workforce 모듈과의 결합을
  인터페이스 뒤로 숨김
- 생성·구성항목 수정·확정·확정취소를 모두 하나의 Unit of Work로 처리하고, 각 처리마다
  이력을 함께 기록(`PY-007`, "모든 정정은 이력으로 남긴다")
- 본인 또는 급여담당자만 조회할 수 있도록 권한 검증(`PY-008`)

### Infrastructure

- Django ORM 모델과 Domain 엔티티를 분리하고 Mapper로 변환
- `payroll_statements`, `payroll_items`, `payroll_history`, `payroll_component_types`,
  `payroll_public_holidays` 신규 테이블 migration 생성(공유 PostgreSQL에 기존
  legacy 테이블이 없어 일반 `makemigrations`로 생성했으며, 공유 DB에는 아직 적용하지
  않았다)
- 기본급/고정수당/초과근무수당(지급), 국민연금/건강보험(장기요양보험 포함)/고용보험(공제)
  6종 구성항목을 초기 데이터 migration으로 등록
- `workforce`의 기존 `Role`/`EmployeeRole` 데이터 모델을 재사용해 `PAYROLL_MANAGER`
  ("급여 담당자") 역할을 workforce 앱 migration으로 시드(기존 `HR_MANAGER`,
  `HR_LEAVE_APPROVER`와 동일한 패턴)
- workforce의 `DjangoWorkforceQueryGateway`, `employee_has_role`을 그대로 재사용해
  급여담당자 권한을 판정

### Presentation

- Django REST Framework 기반 API 구현
- Serializer는 요청 형식 검증만 담당, View는 유스케이스 조립·호출·응답 변환만 담당
- vacation 모듈의 개발용 `X-Employee-No` 헤더 방식 대신, workforce/accounts가 이미
  구축한 실제 세션 인증(`request.user.employee`)과 권한 클래스를 그대로 사용

## 3. 설계상 주요 결정

- **상태 모델링**: Notion 문서의 "작성/정산중 → 확정 → 확정취소 → 작성/정산중 →
  재확정" 흐름 중 실제로 저장하는 상태는 `작성중`/`확정` 두 가지뿐이며, 확정취소·
  재확정은 `PayrollHistory.action`으로 구분되는 이벤트로 구현했다. 재확정 여부는
  이전 확정 이력의 존재로 판정한다.
- **급여 구성항목**: 급여 계산 자동화(4대보험 요율, 소득세 등 법정 공제 계산)는 정확한
  법정 요율 정보 없이 임의로 구현하지 않았다. 대신 구성항목을 참조 테이블로 만들고
  금액은 급여담당자가 `FN-PY-002`에 따라 건별로 직접 입력하는 방식으로 구현했다.
  산재보험은 국내법상 사업주 전액 부담이라 근로자 공제 항목에서 제외했다.
- **정산일자와 공휴일**: 사용자가 확정한 정책(매월 25일, 휴일 시 직전 평일)을
  구현했지만, 실제 국내 공휴일 데이터를 신뢰성 있게 확보하지 못해 `PublicHoliday`
  참조 테이블은 빈 상태로 시작한다. 주말 판정은 자동이며, 공휴일은 담당자가
  Django admin에서 직접 등록해야 정확히 반영된다.
- **역할 관리 API 재사용**: 급여담당자 역할 부여·회수를 위한 별도 API를 만들지
  않고, 기존 `POST /api/workforce/employees/{emp_no}/roles/`를 그대로 사용한다.

## 4. 구현 기능

Notion 기능 명세의 급여 기능을 다음과 같이 반영했다.

1. `FN-PY-001` 급여 정산 생성
2. `FN-PY-002` 급여 구성항목 입력·수정
3. `FN-PY-003` 급여 확정
4. `FN-PY-004` 급여 확정 취소
5. `FN-PY-005` 급여 재확정
6. `FN-PY-006` 사원별 급여 조회
7. `FN-PY-007` 본인 급여명세 조회

## 5. API

모든 엔드포인트는 `/api/payroll/` 아래에 구성했다. 인증은 세션 로그인을 사용하며,
생성·구성항목 수정·확정·확정취소는 `PAYROLL_MANAGER` 역할 또는 슈퍼유저만 수행할 수
있다.

- `GET components/`: 급여 구성항목 목록
- `GET statements/`: 본인 급여 목록(`?emp_no=`로 특정 사원 조회, `?all=true`로 전체
  조회 — 둘 다 급여담당자만 가능)
- `POST statements/`: 급여 생성(급여담당자)
- `GET statements/{id}/`: 급여 상세(본인 또는 급여담당자)
- `PUT statements/{id}/items/`: 구성항목 입력·수정(급여담당자, 작성중 상태만)
- `POST statements/{id}/confirm/`: 확정(급여담당자)
- `POST statements/{id}/cancel-confirmation/`: 확정취소(급여담당자, 사유 필수)
- `GET statements/{id}/history/`: 급여 변경 이력(본인 또는 급여담당자)

## 6. React 화면

- 급여담당자에게는 "내 급여"/"급여 관리" 탭을 제공하고, 일반 사원에게는 본인 급여
  목록만 표시
- 급여 관리 탭에서 사번·정산연월로 급여 생성, 사번으로 필터링 조회
- 구성항목을 지급/공제로 구분한 드롭다운과 금액 입력으로 편집(작성중 상태에서만 노출)
- 확정, 확정취소(사유 입력 프롬프트), 변경 이력 펼쳐보기
- 기존 workforce/vacation 화면과 동일한 스타일 토큰을 재사용

## 7. 테스트 및 검증

공유 PostgreSQL에는 migration을 적용하지 않았다. 모든 테스트는 SQLite 기반이며,
`payroll`은 `workforce.Employee`로의 FK가 있어 테스트에서는 workforce와 마찬가지로
migration 없이 모델을 직접 생성하도록 설정했다(`MIGRATION_MODULES`에 `payroll` 추가).

실행 결과:

- Ruff 검사 통과 (`uv run ruff check .`)
- Django system check 통과
- migration 변경 누락 검사 통과 (`makemigrations --check --dry-run`)
- 전체 pytest 45건 통과 (domain 9건, application/service 5건, API 통합 3건 포함,
  기존 workforce/vacation/accounts 테스트 28건 포함 전체 회귀 확인)
- Frontend ESLint 통과
- Frontend TypeScript 및 Vite production build 통과

## 8. 변경된 주요 영역

- Backend: `payroll` 신규 app(Domain/Application/Infrastructure/Presentation, migration)
- Backend 설정: `payroll` app 및 URL 등록, 테스트용 `MIGRATION_MODULES` 조정

## 9. 후속 작업

1. 국내 공휴일 데이터 확보(수기 등록 또는 외부 API 연동) 및 운영 방침 확정
2. 4대보험 요율·소득세 등 법정 공제 자동계산이 필요해지면 정확한 법정 요율을 확인한
   뒤 계산 로직 추가 검토(현재는 급여담당자 수기 입력)
3. 급여명세 출력/다운로드, 급여 공지(`FN-BD-007`) 등 게시판 모듈과의 경계 기능
4. 대상 환경과 DB 권한을 확인한 뒤 공유 PostgreSQL에 migration 적용
5. Notion MCP 인증 완료 후, 이번 세션에서 반영한 급여 상세 규칙과 정산일자 결정을
   실제 Notion 원문과 교차 검증하고 필요 시 Notion 페이지 자체도 갱신

## 10. 주의사항

- 확정된 급여는 직접 수정할 수 없으며 반드시 확정취소 후 정정하고 재확정한다.
- 상태 변경(생성·구성항목 수정·확정·확정취소)과 이력 생성은 동일한 트랜잭션으로
  처리한다.
- 정산일자 정책(매월 25일, 휴일 시 직전 평일)은 이번 세션에서 담당자가 확정한
  결정이며, Notion 원문 자체는 아직 갱신되지 않았다. Notion 인증 후 교차 확인이
  필요하다.
- 공유 DB에는 명시적인 환경·권한 확인 없이 migration 또는 데이터 쓰기 작업을 실행하지
  않았다.
