# 휴가 신청 잔여일수 표시와 조회 최적화

- 일자: 2026-10-29
- 범위: dev의 vacation application/infrastructure/presentation 및 신청·재신청 UI
- 근거: 저장소 LV-001, FN-LV-001/007. Notion 원문 접근·갱신 없음.

## 구현

기존 `GET /api/vacations/types/`에 선택 옵션 `include_balance=true`를 추가했다. 본인 잔여일수를
유형 응답에 포함하므로 신청 화면의 최초 HTTP 요청 수는 기존과 같은 1회다. 신청·재신청에서만
옵션을 사용하고 다른 목록/승인 화면의 잔여 조회는 추가하지 않는다. 사용자 식별은 기존 세션 또는
명시적 개발 모드 헤더를 따르며 임의 사번 query로 타인의 잔여를 조회하지 못한다.

application port에 일괄 잔여 읽기를 정의했다. DB 어댑터는 이미 읽은 유형의 차감 여부를 재사용하고
본인 잔여 행을 1회 SELECT한다. 개발 어댑터도 승인·실제 차감된 신청만 유형별 SUM 1회로 읽는다.
유형별 반복 조회·새 모델·스키마·캐시·추가 의존성 없이 구현했다. 유형 3개/14개에서 DB 잔여 쿼리
1회를 회귀 검증했다. 이는 쿼리 수 검증이며 공유 원격 DB의 응답 시간 실측은 수행하지 않았다.

잔여 제한 없음(null), 잔여 0일, 확인 불가를 구분한다. 모바일에서도 유형 선택 직후 보이도록 잔여
영역을 선택란 바로 아래에 배치했다. 유형 변경과 일수 입력은 메모리에 받은 결과를 사용한다.
부족 시 안내하지만 프론트의 오래된 값만으로 최종 승인 여부를 결정하지 않는다. 사용자가 명시적으로
새로고침할 수 있으며 중복 요청을 막고, 처리 중 또는 실패한 값은 최신 잔여처럼 표시하지 않는다.
오류 후 재조회에도 사유·일수·유형 입력을 유지한다. 새 신청을 이어 작성하면 잔여도 새로 조회한다.

기존 정책을 유지한다: 대기 신청은 예약 차감하지 않으며 신청/재신청 검증, 승인 시 재검증·차감,
회수 시 복원을 유지한다. DB 차감형 행 누락은 0이고 비차감형은 제한 없음이다. 개발 설정 모드의
미설정 유형은 기존대로 제한 없음이다. 공유 DB/Redis 쓰기나 마이그레이션은 수행하지 않았다.

## 검증

- 백엔드 Ruff 전체 검사, Django test 설정 system check 통과.
- 백엔드 전체 SQLite/fake 테스트 535개 통과. 최종 휴가 관련 집중 실행 34개 통과.
- 본인 조회/타인 헤더·query 무시/미인증 거부/잘못된 식별/옵션 검증/503 응답 회귀 검증.
- DB 일괄 결과와 신청용 개별 잔여 결과 일치, 개발 승인·회수와 대기 미차감 검증.
- 프론트 lint/build 및 59개 테스트 통과. 신청·재신청만 옵션을 보내고 초기 요청을 추가하지 않음을 검증.
- 브라우저는 실제 loader/hook/RequestForm을 임시 진입점에서 합성 fetch로 렌더링했다.
  서버로 실제 데이터를 읽거나 쓰지 않았고 GET 외 요청 및 알 수 없는 경로를 차단했다.
  3.50일/제한 없음/0일·부족 안내, 503 실패 후 입력 유지, 2.50일로 복구를 확인했다.
  유형 3개 전환에도 최초 요청 1회만 발생했다. 320/390/1440px에서 가로 넘침 없고
  잔여 영역이 유형 선택 바로 아래에 표시됨을 확인했다. 임시 검수 파일은 제거했다.
- 사용자 개발 서버/8080 포트의 시작·중지·재시작은 수행하지 않았다.

API 계약, 프론트 계약 가이드 및 통합 현황을 함께 갱신했다. 공유 환경의 실제 잔여 데이터·원격 지연은
이 합성/SQLite 검증에 포함하지 않는다. 실제 신청/승인 시 서버가 최종 잔여를 재검증한다.


## 잔여일수 확인 불가 후속 수정

사용자 제보 후 확인한 프론트 결함: `useState(initial)`로 유형 목록을 복사하면 이전 메타데이터가
남거나 이후 props 변경을 반영하지 못한다. 잔여 없는 이전 유형 목록이 남는 경로를 보완했다.
최신 props를 기본값으로 사용하고 해당 props에 대한 재조회 결과만 덮어쓴다. 잔여 필드가 없는
기존 데이터는 마운트/props 변경 시 1회 자동 재조회한다. 정상 초기 응답에는 추가 조회하지 않는다.
자동 재조회 실패 시 반복 호출하지 않으며 수동 재시도와 폼 입력 유지를 지원한다.

잔여 포함 요청의 응답에서 `remaining_days`가 빠지면 클라이언트가 명시적인 계약 오류로 처리한다.
이전 서버 응답을 성공으로 받아 확인 불가만 표시하지 않고, 서버 최신 변경 반영 확인을 안내한다.
0과 null은 유효한 값으로 유지한다. backend/API 스키마·잔여 정책 변경 없음.

합성 브라우저에서 잔여 없는 초기 목록 → 자동 조회 1회 → 3.50일 표시, 새 props → 4.50일 표시와
추가 조회 없음, 사유 입력 유지를 검증했다. 잔여 없는 서버 응답은 구체적인 오류로 표시되고
자동 무한 재시도하지 않음을 확인했다. 임시 진입점은 삭제했다. frontend lint/build, 61개 테스트 통과.
실제 8080/8000의 미인증 읽기는 모두 403으로 권한을 유지한다. 검수 브라우저가 로그인 전이므로
사용자 계정의 실제 잔여 응답과 제보의 단일 원인을 확정한 것은 아니다. 서버/포트 재시작과 공유 쓰기 없음.


## 실제 실행 환경 후속 진단

사용자가 잔여 데이터가 존재하는데 조회되지 않는다고 재제보하여 실행 프로세스를 확인했다.
8000의 Django는 이 작업의 presentation 코드 변경보다 먼저 시작됐고 `--noreload`로 실행 중이다.
따라서 디스크의 API 수정만으로 실행 중 서버의 응답이 바뀌지 않는다. 통합 실행 스크립트는
macOS/Windows 모두 해당 옵션을 사용하며 루트 README에도 Python 변경 후 재시작을 안내한다.
앞선 프론트 보완만으로 실제 실행 중 API가 갱신되었다고 판단할 수 없다.

추가로 진단 시점에는 localhost 5432 리스너가 없었고 development 설정의 DB 연결도 연결 거부 후
풀 대여 시간 초과로 실패했다. schema/잔여 행 검사는 읽기 전용 트랜잭션으로 계획했으나 연결이
성립하지 않아 실행되지 않았다. 실제 사용자 잔여 행이 없다고 확인한 것이 아니다.
확인한 설정 모드는 database/PostgreSQL이다. 환경 비밀값과 사용자 데이터는 출력하지 않았다.

사용자가 직접 실행을 관리하겠다고 지정한 8080 스택은 시작·중지·재시작하지 않았다.
실제 데이터 검증의 선행 조건은 SSH 포워딩 복구 및 변경된 백엔드 재시작이다.
이번 후속은 실행 환경 진단이며 추가 업무 코드·스키마 변경은 하지 않았다.


## 잔여 표시 문구 중복 수정

고정 제목 `잔여일수`와 상태 값에서 단어가 반복되지 않도록 값을 `제한 없음`, `확인 불가`로
정리했다. 숫자/조회 상태/잔여 정책은 동일하며 프론트 lint/build로 확인했다.
