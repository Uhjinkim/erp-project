# 게시판 기능 구현 및 문서 정리 작업 보고서

- 작업일: 2026-09-22 ~ 2026-10-06
- 작업 브랜치: `board` (최종적으로 `dev`와 동기화·push)
- 대상 DB: SSH 터널로 연결한 공유 개발 PostgreSQL `erp_dev.public`
- 실행 승인: 마이그레이션 적용은 `sqlmigrate`로 DDL을 먼저 공개하고 사용자 승인 후 실행
- 비밀정보: 문서에 기록하지 않음

## 1. 배경

게시판(board) 기능을 신규 바운디드 컨텍스트로 추가하는 작업을 요청받았다. 시작 시점에
저장소 스냅샷(`docs/specs/notion/`)에는 게시판 관련 규칙이 `FN-BD-001`~`007`,
`BD-001`~`008` ID만 나열되어 있고 상세 내용이 없었다.

## 2. 1차 구현과 노션 명세 공백 대응

- 이 세션에는 노션 MCP가 연결되어 있지 않아 원문을 직접 열어볼 수 없었다. 사용자에게
  확인을 요청해 작성 권한, 공지 분류 자동 결정 기준, 수정·삭제 권한 등 상세 규칙 원문을
  직접 전달받았다.
- 받은 내용을 `vacation`/`workforce` 모듈과 동일한 4계층
  (`domain`/`application`/`infrastructure`/`presentation`) 구조로 구현하고, 저장소
  스냅샷(`02`~`04-*.md`)에도 상세 내용을 반영했다(이후 7장에서 되돌림).
- 사용자가 MVP 범위를 "글 CRUD + 목록/상세만"으로, 삭제 방식을 "소프트 삭제"로 확정했다.
- 백엔드 테스트(pytest) 49개가 모두 통과하는 상태로 1차 구현을 마쳤다.

## 3. 로그인·개발 서버 기동 문제: 원인과 해결

사용자가 실제 화면에서 기능을 확인하려는 과정에서 다음 문제가 연속으로 드러났다.

| 증상 | 원인 | 해결 |
| --- | --- | --- |
| 로그인 시 "요청을 처리하지 못했습니다"만 표시 | 프론트 `requestJson`이 에러 응답의 `detail` 필드만 읽고 `non_field_errors`는 무시 | `extractErrorMessage` 헬퍼를 추가해 `non_field_errors`도 읽도록 수정(`frontend/src/api/client.ts`) |
| 수정 후에도 로그인 403 (`CSRF Failed: Origin checking failed`) | `bun run dev`(5173)와 `manage.py runserver`(8000)를 따로 띄워 브라우저 기준 cross-origin 요청이 됨 | 저장소 표준 기동 스크립트 `scripts/start-dev.ps1`로 nginx(8080)·backend·frontend를 함께 띄워 동일 origin으로 통일 |
| `start-dev.ps1` 재실행 시 "Port 8080 is already in use" | 이전 검증에서 띄운 nginx 프로세스가 backend/frontend는 죽고 nginx만 포트를 쥔 채 남음(좀비 프로세스) | 해당 nginx 프로세스를 종료하고 재기동 |

## 4. 실제 공유 DB 스키마 불일치 발견과 전면 재설계

읽기 전용으로 공유 DB 스키마를 확인하는 과정에서 `board_posts`,
`board_notice_categories` 테이블이 **이미 존재**한다는 사실을 발견했다. 1차 구현은 이
사실을 모른 채 작성되어 다음이 실제 스키마와 달랐다.

- 소프트 삭제용 `deleted_at` 컬럼이 실제 테이블에 없었다(당시 기준).
- `notice_category`가 문자열 컬럼이 아니라 `board_notice_categories`를 참조하는 FK였다.
- `writer_emp_no`가 단순 정수 컬럼이 아니라 `employees`를 참조하는 FK였다.

사용자가 "DB 자체를 수정하는 작업은 모두 제외"하고 실제 스키마에 맞춰 코드를 전면
재작성하도록 결정해, domain/application/infrastructure 전 계층과 마이그레이션을
실제 컬럼명·FK 구조에 맞춰 다시 작성했다(이 시점에는 삭제를 하드 삭제로 임시 전환).
`board_notice_categories`가 당시 빈 테이블이어서 코드 값(`MANAGEMENT`/`HR`/`PAYROLL`/
`DEPARTMENT`)은 이번에 새로 결정했다.

## 5. 기능 확장 요청과 반영

이후 사용자가 다음 5가지를 추가로 요청해 반영했다.

1. **소프트 삭제 복원** — `board_posts.deleted_at` 컬럼을 추가하는 마이그레이션을
   새로 작성해 하드 삭제를 소프트 삭제로 되돌렸다.
2. **댓글/대댓글 기능** — 신규 테이블 `board_comments`를 설계했다(공유 DB에 해당 테이블이
   없음을 사용자가 재확인). `parent_comment_id`로 1단계 답글만 허용하고 소프트 삭제로
   처리한다.
3. **목록 간소화** — 게시판 목록에는 제목·유형·작성자·날짜만 노출하고, 본문과 수정 기능은
   상세 화면으로 분리했다(`frontend/src/components/BoardPanel.tsx` 전면 재작성).
4. **상세 화면 수정 버튼** — 상세 화면에서 본인 작성 글일 때만 수정·삭제 버튼을 노출한다.
5. **검색 기능** — 제목/작성자를 선택하는 드롭다운과 검색창을 추가했다. 작성자 검색을
   의미 있게 하기 위해 게시글 응답에 `writer_name`을 추가했다(`Employee.person.name`을
   `select_related`로 조인하는 순수 조회 확장, 스키마 변경 아님).

## 6. 마이그레이션 적용

1. `uv run python manage.py makemigrations board`로 마이그레이션 파일만 생성하고 적용은
   보류했다.
2. 사용자 요청에 따라 `uv run python manage.py sqlmigrate board 0002`로 실제 실행될 DDL
   (`ALTER TABLE board_posts ADD COLUMN deleted_at`, `CREATE TABLE board_comments` 및 FK·
   인덱스)을 먼저 공개했다.
3. 사용자 승인 후 SSH 터널이 열린 상태에서 `uv run python manage.py migrate board`를
   실행해 공유 개발 DB에 적용했다(`0001_initial`은 상태 등록만, `0002_*`는 실제 DDL).
4. 적용 후 `/api/health/`와 `information_schema` 조회로 `deleted_at` 컬럼과
   `board_comments` 테이블이 `erp_dev.public`에 실제로 존재함을 읽기 전용으로 재확인했다.

`board_notice_categories` 시드 데이터(코드 4건) 삽입은 공유 DB 데이터 쓰기에 해당해 이번
범위에서 제외했다 — 시드 전까지 공지 작성은 FK 제약으로 운영 DB에서 실패한다.

## 7. 문서 체계 정리: 원인과 해결

작업 도중 팀원(Uhjinkim)이 별도로 `docs: standardize specs and collaboration workflow`
커밋을 `dev`에 올려, 기능 브랜치가 공용 문서(`docs/specs/`, `docs/reports/`, `docs/guides/`,
루트 `README.md`)를 직접 수정하지 않고 `docs/contributions/<module>/<branch-slug>/README.md`
에만 기록하는 새 협업 규칙(`docs/guides/module-branch-docs-workflow.md`)이 도입되었다.
이 규칙이 도입되기 전에 1차 구현에서 이미 `02-business-rules.md`,
`03-feature-specification.md`, `04-detailed-features.md`,
`docs/specs/notion/README.md`를 직접 수정하고 `board-implementation-map.md`를 새로
추가한 상태였다.

또한 `board`를 `dev`에 병합한 커밋(`docs 반영`, 499deb9)에서 `docs/specs/notion/README.md`가
두 브랜치 모두 수정한 충돌을 해결하는 과정에서 **파일 전체가 삭제되는 실수**가 있었던 것을
확인했다.

대응:

- `./scripts/docs-workflow.ps1 init board`로 `docs/contributions/board/board/README.md`를
  생성하고, 게시판 기능의 범위·설계 결정·API/스키마 영향·검증 결과·공용 문서 반영 후보를
  정리해 기록했다(스크립트가 생성한 초안은 PowerShell 5.1 인코딩 문제로 한글이 깨져 있어
  직접 다시 작성했다).
- `02`/`03`/`04-*.md`를 게시판 작업 이전 커밋(`d284487^`) 기준으로 되돌렸다(이 세 파일은
  게시판 작업 외 다른 변경이 없어 안전하게 되돌릴 수 있었다).
- `board-implementation-map.md`를 삭제했다(Git 이력에는 남아 있고, 내용은 기여 문서로
  이전).
- `docs/specs/notion/README.md`를 팀원이 추가한 "설계 명세 스냅샷"/"구현 대응 문서" 구조를
  유지한 채 복구하고, 게시판 전용 링크만 제외했다.

## 8. 브랜치 동기화와 push

작업 시작 시점에 이미 `board`가 `dev`에 병합되어 `board`/`dev`/`origin/board`/`origin/dev`가
모두 동일 커밋(499deb9)이었다. 문서 정리 커밋(7e51f0c)을 `board`에서 생성한 뒤, `dev`를
동일 커밋으로 fast-forward하고 두 브랜치를 모두 `origin`에 push했다(강제 push 없이 일반
fast-forward push로 완료).
