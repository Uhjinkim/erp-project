# 급여 모듈 레거시 스키마 불일치 수정 보고서

- 작업일: 2026-09-23
- 작업 범위: 급여 모듈 백엔드 스키마 수정 및 공유 개발 DB migration 적용
- 계기: 사용자가 급여담당자 role로 로그인 후 급여 탭 진입 시 "요청을 처리하지
  못했습니다" 오류 보고(급여 등록 불가, 본인 급여 미표시)
- 참고: 이 보고서는 2026-09-22 `docs/reports/2026-09-22_급여_모듈_작업_보고서.md`에서
  구현한 급여 모듈의 후속 수정이다.

## 1. 사용자 보고 내용

1. 급여담당자 role로 급여 탭에 들어갔을 때 급여 등록이 되지 않는다.
2. 본인 급여도 조회되지 않는다.
3. Notion MCP 인증은 앞으로도 계속 불가능하므로, 필요한 정보는 Claude가 직접
   사용자에게 물어봐야 한다.

## 2. 원인

공유 PostgreSQL(`erp_dev`)에는 급여 관련 legacy 테이블 4개(`payrolls`,
`payroll_details`, `payroll_items`, `payroll_history`)가 이미 존재하고 있었다. 이
사실은 저장소 루트의 `erp_dev.md`(2026-09-20 작성, ERD 포함)에 이미 문서화되어
있었지만, 2026-09-22 급여 모듈을 처음 설계할 때 이 문서를 확인하지 않았다. 그 결과
`payroll_statements`, `payroll_component_types` 등 실제로는 존재하지 않는 새 이름의
테이블을 기대하는 Django 모델과 일반 `CreateModel` migration으로 구현했다.

공유 DB에는 이 migration을 적용하지 않았으므로(2026-09-22 보고서 6절에 명시),
실제 서버가 이 코드로 API를 처리하려 하면 대상 테이블이 없어 매 요청마다 데이터베이스
오류(500)가 발생했다. 프론트엔드는 이 500 오류를 상세 메시지 없이 "요청을 처리하지
못했습니다"로만 표시했기 때문에(`frontend/src/api/client.ts`의 fallback 메시지),
사용자에게는 원인이 보이지 않았다. 급여 등록(POST)과 본인 급여 조회(GET) 모두 같은
이유로 실패했다 — "DB에 데이터가 없어서"가 아니라 "존재하지 않는 테이블을 조회해서"였다.

## 3. 조치

### 3.1 실제 스키마 재확인 (읽기 전용)

`information_schema`와 `pg_constraint`를 읽기 전용으로 조회해 4개 legacy 테이블의
컬럼, 제약조건, FK를 전부 확인했다. CHECK 제약에 포함된 한글 허용값(`status`,
`item_type`, `action`)은 셸 출력 과정에서 깨져 보여, 담당자에게 직접 확인을 요청했다
(작성중/확정, 지급/공제, 확정/확정취소/재확정/수정). 이후 파일로 저장해 다시 읽어보니
DB에 저장된 실제 값은 깨지지 않은 정상 UTF-8이었다 — 깨짐은 셸 출력 단계에서만
발생한 것으로 보인다. 담당자가 확인해 준 값은 실제 값과 일치했다.

### 3.2 백엔드 코드 수정

- `payroll/infrastructure/models.py`: 4개 legacy 테이블에 정확히 매핑되도록 모델을
  다시 작성했다(`db_table`, `db_column`을 실제 컬럼명에 맞춤). `PayrollDetailModel`
  (`payroll_details`)에는 category 컬럼이 없어, 지급/공제 구분은 `payroll_items`
  join으로 얻도록 변경했다.
- `payroll/migrations/`: workforce/vacation과 동일하게 4개 legacy 테이블은
  state-only migration(`SeparateDatabaseAndState`, 실제 DDL 없음)으로, 새 테이블인
  `payroll_public_holidays`만 일반 `CreateModel`로 분리했다.
- `payroll/domain/entities.py`: `PayrollStatement`에서 실제 테이블에 없는
  `created_by` 필드를 제거했다(생성자는 별도로 기록하지 않는다). `PayrollHistory`의
  `change_summary`를 제거하고 `reason` 컬럼 하나로 통합했다. `PayrollAction`에서
  `생성`을 제거했다 — 실제 `payroll_history.action` CHECK 제약이 `확정`/`확정취소`/
  `재확정`/`수정` 4개만 허용하고 `생성`은 포함하지 않기 때문이다.
- `PayrollStatement.net_pay`에서 원 단위 올림 처리를 제거했다. 실제 `payrolls`
  테이블이 `net_pay = total_pay - total_deduct`를 정확히 일치하도록 CHECK 제약으로
  강제하므로, 별도 반올림을 적용하면 그 제약을 위반한다.
- `payroll/application/service.py`: 급여 생성 시 이력을 남기지 않도록 수정했다(위와
  동일한 이유). 구성항목 변경 요약은 `reason` 컬럼(varchar(255))에 담되 255자를
  초과하면 잘라서 저장하도록 방어 코드를 추가했다.
- 관련 테스트(`test_payroll_domain.py`, `test_payroll_service.py`,
  `test_payroll_api.py`)를 수정된 도메인 모델과 이력 action 집합에 맞게 갱신했다.

### 3.3 변경 후 스키마 대조

Django 모델의 컬럼과 실제 PostgreSQL 컬럼을 `information_schema`로 다시 대조해
4개 테이블 모두 불일치 0건을 확인했다.

### 3.4 공유 개발 DB 적용

사용자 승인을 받아 `uv run python manage.py migrate`를 실행했다. 적용 전 계획
(`--plan`)으로 실제 변경 범위를 먼저 확인했다.

- `payroll.0001_initial`: 4개 legacy 테이블 상태 등록(실제 DDL 없음)
- `payroll.0002_public_holiday`: `payroll_public_holidays` 신규 테이블 생성
- `payroll.0003_seed_components`: `payroll_items`에 구성항목 6건 시드
  (`get_or_create`, 기존 데이터 없어 충돌 없음)

적용 전 `payrolls`/`payroll_details`/`payroll_history`/`payroll_items`는 모두 0건이었고,
적용은 기존 데이터를 건드리지 않았다. 적용 후 `payroll_items`에 6건이 정상 삽입된 것과
실제 서비스 계층(`PayrollService.list_components()`)이 실 DB에서 예외 없이 동작하는
것을 확인했다.

`django_migrations`에는 이전(2026-09-22 원래 스키마 기준) 상태로 보이는
`payroll.0001_initial`, `payroll.0002_seed_components`, `workforce.0003_payroll_manager_role`
적용 기록이 이미 남아 있었다 — 이 세션에서 `migrate`를 실행하기 전에 발견한 상태다.
`roles` 테이블에는 실제로 `PAYROLL_MANAGER` 행이 존재해 그 기록은 유효했지만,
`payroll_items`는 이때도 0건이었고 `payroll_statements`, `payroll_component_types`,
`payroll_public_holidays` 같은 잘못된 이름의 테이블은 전혀 만들어지지 않은 상태였다.
정확한 경위는 확인하지 못했으나(사용자가 별도로 `migrate`를 시도했을 가능성이 있음),
실제 DB에 부작용이 없었음을 읽기 전용 조회로 확인한 뒤 진행했다.

## 4. 검증

- Django system check, `ruff check`, `makemigrations --check --dry-run` 통과
- pytest 44건 통과(급여 도메인/서비스/API/아키텍처 테스트 포함)
- 공유 개발 DB 대상으로 `PayrollService.list_components()`를 직접 호출해 예외 없이
  6건을 반환하는 것을 확인(실제 API가 호출하는 것과 동일한 코드 경로)
- 사용자 계정에 `PAYROLL_MANAGER` role이 이미 6건 활성 부여되어 있음을 확인(집계값만
  확인, 대상자 식별 정보는 조회하지 않음)

프론트엔드에서 급여 탭 진입, 급여 생성, 본인 급여 조회가 정상 동작하는지는 사용자가
직접 확인해야 한다.

## 5. 교훈과 후속 조치

- **새 Django app을 만들기 전에는 `erp_dev.md`와 실제 DB(`information_schema`)부터
  확인한다.** 이번 문제의 근본 원인은 이 확인을 건너뛴 것이다. 게시판(`board_posts`,
  `board_notice_categories`), 개인정보 변경요청(`employee_change_requests`),
  인사평가(`evaluations`) 등 아직 구현하지 않은 다른 모듈에도 이미 legacy 테이블이
  존재하므로, 앞으로 이 모듈들을 구현할 때도 반드시 먼저 대조해야 한다.
- Notion MCP는 이 환경에서 계속 인증 불가능하다고 안내받았다. 앞으로 Notion 원문이
  필요하면 MCP 인증을 기다리지 않고 사용자에게 직접 질문한다.
- 자동 테스트는 SQLite에 모델을 직접 생성하는 방식이라(legacy 테이블에 대한
  `MIGRATION_MODULES=None` 설정), 이번처럼 "Django 모델과 실제 legacy 테이블 이름·
  컬럼이 어긋나는" 유형의 문제는 테스트만으로 잡히지 않는다. 새로운 legacy 매핑을
  추가할 때는 테스트 통과와 별개로 실제 스키마 대조를 항상 거쳐야 한다.
- 공휴일 데이터, 4대보험 요율 자동계산 등 후속 과제는 기존
  `payroll-implementation-map.md`의 후속 구현 목록과 동일하다.
