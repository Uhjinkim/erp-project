# 공유 개발 DB 연결·마이그레이션 작업 보고서

- 작업일: 2026-09-20
- 대상: SSH 로컬 포워딩을 통해 연결한 공유 개발 PostgreSQL
- Django 환경: `development`
- 접점: `127.0.0.1:5432`
- 실행 승인: 사용자 확인 후 실제 migration 적용
- 비밀정보: 문서에 기록하지 않음

## 1. 연결 및 적용 전 검사

Django가 PostgreSQL backend와 development 설정을 사용하고 있음을 확인하고, 다시 열린
SSH 터널을 통해 DB 연결을 검증했다. 현재 DB 사용자에게 대상 schema의 `CREATE` 권한이
있음을 확인했다.

기존 legacy 테이블 10개의 실제 컬럼과 Django model state를 읽기 전용으로 대조했다.

- `persons`
- `positions`
- `roles`
- `departments`
- `employees`
- `emp_history`
- `employee_roles`
- `leave_types`
- `leave_requests`
- `leave_request_history`

모든 테이블의 누락·초과 컬럼은 0개였다. 생성 예정이던 Django 기본 테이블,
`accounts_users`, `leave_balances`, `django_migrations`는 적용 전에 존재하지 않아 이름 충돌이
없었다.

데이터 내용은 출력하지 않고 집계값만 검사했다.

- 사내 이메일 대소문자 중복 그룹: 0
- 활성 사원 역할 중복 그룹: 0
- 존재하지 않는 Person을 참조하는 Employee: 0
- 존재하지 않는 상위 부서를 참조하는 Department: 0

## 2. 적용 명령

Backend 디렉터리에서 다음 명령을 실행했다.

```bash
uv run python manage.py migrate --noinput
```

## 3. 적용 결과

다음 app의 migration 23건이 모두 정상 적용됐다.

- `workforce`: legacy schema state 등록 및 필수 역할 보장
- `contenttypes`, `auth`, `admin`, `sessions`: Django 기본 테이블 생성
- `accounts`: ERP 사용자·그룹·권한 연결 테이블 생성
- `vacation`: legacy schema state 등록 및 `leave_balances` 생성

`workforce.0001_initial`과 `vacation.0001_initial`은 기존 legacy 테이블을 다시 만들지 않는
state-only migration이다. 신규 DB 객체를 만드는 migration과 구분해 적용됐다.

## 4. 적용 후 검증

- `showmigrations --plan`: 전체 항목 `[X]`
- Django database system check: 이상 없음
- PostgreSQL 재연결: 성공
- `django_migrations` 기록: 23건
- 신규 테이블 존재 확인: 모두 성공
  - `django_migrations`
  - `django_content_type`
  - `auth_permission`, `auth_group`
  - `accounts_users`
  - `django_admin_log`
  - `django_session`
  - `leave_balances`
- 필수 역할 존재 확인: `HR_MANAGER`, `HR_LEAVE_APPROVER`

## 5. 변경 범위와 후속 작업

이번 작업은 schema migration과 필수 역할의 멱등 생성까지만 수행했다. 슈퍼유저·사원 계정,
EmployeeRole 배정, 휴가 잔여일수 데이터는 생성하거나 수정하지 않았다.

후속 작업은 대상 사용자와 초기 데이터 원천을 확인한 뒤 별도 승인하에 수행한다.
운영 DB에는 이번 development 적용 결과를 그대로 복제하지 말고 staging 리허설과 백업 확인을
다시 거쳐야 한다.
