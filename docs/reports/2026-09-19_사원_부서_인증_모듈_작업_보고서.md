# 사원·부서·인증 모듈 작업 보고서

- 작업일: 2026-09-19
- 작업 범위: 기존 ERP 인사 스키마 매핑, 이메일 로그인, 서버 세션 인증, 휴가 모듈 연동
- 기준 스키마: 저장소 `erp_dev.md`의 실제 운영 테이블 ERD

## 1. 작업 개요

기존 PostgreSQL의 사원·부서·직급·역할 테이블을 Django `workforce` 앱으로 매핑하고,
이메일을 로그인 ID로 사용하는 `accounts` 앱을 구현했다. 브라우저 인증은 JWT를 저장하지 않고
Django 서버 세션과 HttpOnly 쿠키를 사용한다.

기존 테이블에는 Django migration 이력이 없으므로 초기 migration은 테이블을 다시 생성하지 않고
`SeparateDatabaseAndState`로 모델 상태만 등록하도록 구성했다. 새 인증 테이블과 휴가 잔여일수
테이블은 별도의 실제 schema migration으로 분리했다. 공유 DB에는 migration을 실행하지 않았다.

## 2. 모듈 구조

### Workforce

- `Person`: 이름, 생년월일, 성별
- `Employee`: 사번, 인적사항, 소속 부서, 직급, 재직상태, 연락처와 입·퇴사일
- `Department`: 상위 부서와 부서장 관계
- `Position`: 직급 코드와 정렬 순서
- `EmploymentHistory`: 사원 발령·부서·직급·급여 이력
- `Role`, `EmployeeRole`: 역할과 역할 부여·회수 이력

사원과 부서는 부서장과 소속 관계가 서로 참조하므로 하나의 bounded context와 Django 앱으로
구성했다. 부서 이동 시 순환 계층을 차단하고, 재직 중이며 해당 부서에 소속된 사원만 부서장으로
지정하도록 API 입력을 검증한다.

### Accounts

- Django `AbstractUser` 기반 커스텀 User
- `username` 제거, 정규화된 이메일을 `USERNAME_FIELD`로 사용
- User와 Employee를 선택적 1:1 관계로 연결
- 대소문자를 무시하는 이메일 unique 제약 추가
- Django session authentication과 CSRF 보호 적용
- 퇴사·휴직 사원의 로그인 및 인증 API 사용 차단
- 사원이 비재직 상태로 저장되면 연결된 계정을 비활성화

### Vacation integration

- 운영 `WorkforceGateway`가 실제 Employee, Department, EmployeeRole을 조회
- 소속 부서의 재직 중 부서장을 1차 승인자로 결정
- 부서장이 없거나 신청자 본인이 부서장이면 단일 `HR_LEAVE_APPROVER`를 fallback으로 사용
- 활성 `HR_MANAGER` 역할로 인사관리자 권한 판단
- 신규 `leave_balances` 테이블을 휴가 도메인 소유로 추가
- 차감형 휴가에 잔여일수 행이 없으면 0일로 처리하여 fail-closed

## 3. 인증 흐름

1. 프론트가 `GET /api/auth/csrf/`로 CSRF 쿠키를 받는다.
2. 이메일과 비밀번호를 `POST /api/auth/login/`으로 전송한다.
3. Django가 비밀번호, 계정 활성 여부, 사원 재직상태를 확인한다.
4. 성공하면 최대 8시간의 서버 세션을 발급한다.
5. 프론트는 `GET /api/auth/me/`로 사원·부서·직급·역할을 조회한다.
6. 상태 변경 요청은 중앙 API 클라이언트가 `X-CSRFToken`을 자동 첨부한다.
7. 로그아웃은 서버 세션을 폐기한다.

브라우저에는 인증정보 대신 HttpOnly 세션 ID만 저장한다. production build에서는 개발 사원 선택과
`X-Employee-No`를 사용하지 않으며, 인증된 User에 연결된 Employee로 요청 사용자를 식별한다.

## 4. 승인자 결정 규칙

승인자는 다음 순서로 결정한다.

1. 신청자의 현재 부서를 조회한다.
2. 신청자와 다른 재직 중 부서장이 있으면 승인자로 지정한다.
3. 부서장이 없거나 신청자 본인이 부서장이면 활성 `HR_LEAVE_APPROVER`를 조회한다.
4. 활성 담당자가 정확히 한 명일 때만 승인자로 지정한다.
5. 담당자가 없거나 여러 명이면 승인자를 결정하지 못한 것으로 처리한다.

`HR_MANAGER`는 인사 데이터 관리 권한이고 `HR_LEAVE_APPROVER`는 휴가 fallback 승인 책임이므로
역할을 분리했다. 초기 역할 migration은 없는 역할만 생성하며 기존 역할명이나 배정을 덮어쓰지 않는다.

## 5. API

### 인증

- `GET /api/auth/csrf/`: CSRF 쿠키 발급
- `POST /api/auth/login/`: 이메일 로그인과 세션 발급
- `POST /api/auth/logout/`: 서버 세션 폐기
- `GET /api/auth/me/`: 현재 계정·사원·조직·역할 조회
- `/api/auth/accounts/`: HR 관리자용 계정 관리

### 사원·조직

- `/api/workforce/persons/`: HR 관리자용 인적사항 관리
- `/api/workforce/employees/`: 사원 조회·관리와 검색
- `/api/workforce/employees/{emp_no}/roles/`: 역할 조회·부여
- `/api/workforce/employees/{emp_no}/roles/{id}/revoke/`: 역할 회수
- `/api/workforce/departments/`: 부서 조회·관리
- `/api/workforce/positions/`: 직급 조회·관리
- `/api/workforce/roles/`: 역할 조회

일반 인증 사용자는 사원·부서·직급을 조회할 수 있고, 생성·변경과 민감 인적사항 API는
슈퍼유저 또는 활성 `HR_MANAGER`만 사용할 수 있다.

- 기존 연결 상태와 오프라인 시뮬레이션 유지

## 7. Migration 정책

- `workforce/0001_initial`: 기존 인사 테이블의 Django state만 등록하며 DB 작업 없음
- `workforce/0002_required_roles`: 필요한 HR 역할이 없을 때만 추가
- `accounts/0001_initial`: 신규 계정, 그룹, 권한 연결 테이블 생성
- `vacation/0001_initial`: 기존 휴가 테이블의 Django state만 등록하며 DB 작업 없음
- `vacation/0002_leavebalancemodel`: 신규 `leave_balances` 테이블 생성

적용 전 실제 PostgreSQL의 컬럼 nullability, FK, sequence, 기존 중복 이메일과 orphan 데이터를
반드시 읽기 전용으로 대조해야 한다. 이번 작업 시 SSH 터널이 열려 있지 않아 실제 DB introspection은
수행하지 않았다. `--fake-initial`만으로 적용하지 않고 migration SQL과 상태를 검토해야 한다.

## 8. 검증

- Django system check 통과
- Ruff 검사 통과
- 이메일 대소문자 정규화 로그인 확인
- CSRF 보호 로그인 및 서버 세션 발급 확인
- 비재직 사원 로그인 차단 확인
- 일반 사원의 부서 생성 권한 차단 확인
- HR 관리자의 부서 생성 확인
- 부서장 부재 시 HR 휴가 승인담당자 fallback 확인
- 세션 사용자 → 실제 WorkforceGateway → 휴가 신청·승인 통합 흐름 확인
- 기존 휴가 도메인 및 API 회귀 테스트 통과
- Frontend ESLint, TypeScript, production build 통과

공유 PostgreSQL에 migration, seed, 계정 생성 또는 데이터 변경은 실행하지 않았다.

## 9. 적용 전 운영 체크리스트

1. SSH 터널을 열고 기존 스키마를 read-only introspection한다.
2. 이메일 `NULL`, 빈 값, 대소문자 중복과 공유 이메일을 검사한다.
3. 없는 사원·부서·직급·역할을 참조하는 orphan 데이터를 검사한다.
4. 부서 계층 순환과 여러 활성 `HR_LEAVE_APPROVER` 배정을 검사한다.
5. 별도 staging DB에서 전체 migration을 리허설한다.
6. 최초 슈퍼유저를 생성하고 Employee와 연결한다.
7. 필요한 사원 계정을 생성하고 HR 역할을 배정한다.
8. `leave_balances` 초기 데이터를 검증된 원천에서 적재한다.
9. 로그인 → 휴가 신청 → 부서장 또는 HR 승인 E2E를 수행한다.
10. 대상 환경과 권한을 재확인한 뒤 승인받아 공유 DB에 적용한다.
