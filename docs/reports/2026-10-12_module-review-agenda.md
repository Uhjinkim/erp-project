## 공통 전제

기여 문서의 “사용자·담당자 확정” 기록과 현재 공용 명세는 구분한다. 기존 명세 밖 추가 규칙·기능은
이번 통합에서 제외했으며 코드에서 자동 제거한 것은 아니다. 아래 작업은 담당자에게 할당할
검토·수정 범위이며, 공유 DB migration·seed·데이터 수정이나 자동 메시지 전송을 승인하지 않는다.

현재 화면은 이전에 결정한 디자인 시안으로 재설계한다. 기존 UI의 배치·필터·표시 순서·댓글 화면은
정본으로 채택하지 않는다. 시안의 구체 파일·버전은 이번 검토에서 확인하지 않았으므로 UI 작업 전에
담당자가 해당 시안을 확인한다. 재설계와 별개로 API 권한과 데이터 로딩 문제는 해결해야 한다.

## INT-01 · 사원 조회 권한과 평가·급여 화면 연동

- 담당: workforce 주관, evaluation·payroll·frontend 협업.
- 관련 기준: HR-001, FN-EV-001·FN-EV-004, FN-PY-006, 역할 권한 독립 합산.
- 현재 동작: [사원 뷰](../../backend/workforce/presentation/views.py)는 목록을 HR 전용으로 제한한다.
  [평가 화면](../../frontend/src/components/EvaluationPanel.tsx)은 평가 목록과
  [loadWorkforce](../../frontend/src/api/workforce.ts)를 Promise.all로 호출한다.
  [급여 화면](../../frontend/src/components/PayrollPanel.tsx)은 사원 조회 성공 후 관리 목록을 불러온다.
- 재현 조건·영향: HR이 아닌 사용자의 사원 목록 요청은 403. 평가 화면은 본인 평가 조회에도
  해당 요청을 실행해 목록 반영이 실패한다. HR이 아닌 급여담당자는 관리 대상자·급여 목록 로딩이 중단된다.
  급여의 본인 목록은 이 호출 전에 설정하므로 본인 조회 전체가 차단된다고 단정하지 않는다.
- 작업: 부서장의 관리 대상, 급여담당자의 급여 대상 등 업무별 필요한 최소 조회 범위를 설계하고
  화면 호출을 분리한다. 전체 인사정보 API를 일반 공개하는 방식으로 해결하지 않는다.
- 결정 요청: 최소 조회 포트·API의 소유 모듈, 응답 필드와 역할별 범위.
- 완료 기준: 일반 사원 본인 평가 조회, 부서장 평가 작성 대상, 비HR 급여담당자 관리 화면이 동작한다.
  비허용 인사정보 접근은 계속 차단한다. 각 역할의 성공·권한 밖 실패와 실제 화면 회귀를 검증한다.
- 인프라 영향: API 설계에 따라 판단. DB 쓰기 승인 없음.

## BD-01 · 공지 분류 범위와 복수 담당자 권한

- 담당: board, 제품·문서 담당 협업.
- 관련 기준: BD-003·BD-004·BD-007·BD-008.
- 근거: 원문 BD-008은 역할·권한별 자동 부여와 임의 변경 금지다.
  원문 BD-004·BD-007에는 부서 분류가 있으나 사용자는 “부서장 공지는 따로 없음”으로 설명했다.
- 현재 동작: [gateway](../../backend/board/infrastructure/workforce_gateways.py)는
  경영·인사·급여 Role과 Department.head를 자격 집합으로 반환한다.
  [서비스](../../backend/board/application/service.py)는 클라이언트가 보낸 분류가 그 집합에 있는지만 검사한다.
- 영향: 시스템 자동 결정과 자격 범위 내 선택이 다르다. 복수 담당자 권한은 규칙상 허용된다.
- 작업: 담당자 Role에 따른 자격 산정은 유지하되, 부서 공지 제외 여부 및 기존 부서 공지 처리 방향을 검토한다.
  단일 담당자 권한 자동 부여와 복수 담당자 권한 처리 방식을 결정한 후 서버에서 강제한다.
- 결정 요청: 부서 분류 존치/제외 및 기존 데이터 처리, 복수 담당자에게 자격 범위 내 선택을 허용할지.
  선택 허용은 이번 대화에서 논의했으나 최종 결정으로 기록하지 않는다. 역할 우선순위도 임의로 만들지 않는다.
- 완료 기준: 확정된 분류 범위, 단일·복수·무자격·권한 밖 분류, 작성 후 분류 변경을 테스트한다.
  BD-004·BD-007·BD-008과 API·테이블 문서를 함께 정리한다.
- 인프라 영향: 코드 수정 외 분류 마스터·기존 글 데이터 영향은 별도 승인 필요.

## BD-02 · 댓글·대댓글 등 추가 기능

- 담당: board, 제품·문서 담당 협업.
- 기준: FN-BD-001~FN-BD-007은 글 작성·수정·삭제·목록·상세·급여 공지이며 댓글 정의는 없다.
- 현재 동작: 댓글 API, 1단계 답글 제한, board_comments가 구현되어 있다.
- 작업: 이번 제품 명세 통합에서는 댓글·답글 깊이 규칙을 제외한다.
  기존 구현·데이터를 유지할지 별도 기능으로 제안할지는 담당자가 기여 초안에 기록한다.
  삭제의 기술 방식인 board_posts.deleted_at은 댓글 기능과 구분한다.
- 결정 요청: 추가 기능을 별도 명세로 제안할지, 제품 범위에서 제외할지.
- 완료 기준: 승인되지 않은 기능을 기존 FN-BD ID의 구현 완료로 연결하지 않는다.
  범위를 바꾸면 기존 데이터·API 이용 영향과 회귀 검증을 제시한다.
- 인프라 영향: 테이블·데이터 제거는 승인 전 실행 금지.

## EV-01 · HR 역할이 있는 부서장의 평가 작성

- 담당: evaluation, workforce 협업.
- 기준: EV-001·EV-004, FN-EV-001, 복수 역할의 독립 권한 합산.
- 현재 동작: [평가 도메인](../../backend/evaluation/domain/entities.py)의
  ensure_not_hr_manager_evaluator는 부서장이 HR 역할도 보유하면 작성·수정·제출·재배정 후보 자격을 제한한다.
- 영향: HR 역할을 추가하면 기존 부서장 작성 권한이 사라지고 해당 부서 평가 생성이 막힐 수 있다.
- 작업: 공용 명세에 없는 일괄 금지와 역할 합산 원칙을 대조해 수정안을 작성한다.
  “부서장 작성 / HR 확정”이라는 수행 주체 정의만으로 동일인의 역할 겸직 금지를 추론하지 않는다.
- 결정 요청: 작성자·확정자 동일인 금지 등 별도 직무 분리 규칙을 둘 것인지(EV-02와 연계).
- 완료 기준: HR 역할 유무에 따른 부서장 작성 권한, 자기평가 금지, 비부서장의 작성 차단을 검증한다.
  이전 담당자 확인 기록을 공용 규칙으로 자동 승격하지 않는다.
- 인프라 영향: 권한 정책 수정. DB 쓰기 승인 없음.

## EV-02 · 평가 상태·운영 정책 확대

- 담당: evaluation, 제품·문서 담당 협업.
- 기준: 공용 상태는 작성중 → 확정, 확정된 본인 평가 공개.
- 현재 동작: 제출을 거쳐야 확정할 수 있고 반려·재배정·제외·제외취소·확정취소가 있다.
  상위 부서장 평가, 연말 조직 판정·현재 조직 fallback, 생성 연도 제한,
  작성 관여자 확정 금지·본인 HR 동작 금지·이력 공개 제한·동시 수정 정책도 추가되었다.
- 작업: [기여 초안](../contributions/evaluation/bae/README.md)의 각 추가 정책을 기존 규칙과 분리한다.
  추가 정책을 채택할지 기존 흐름에 맞출지 검토하되 현재 DB 상태·진행 중 평가·이력 보존을 먼저 조사한다.
- 결정 요청: 추가 상태·정정·평가자 배정 정책의 채택 여부, 조직 기준일·연도 제한·이력 공개·동시 수정 기준.
- 완료 기준: 결정된 상태 전이·권한·열람 성공/실패와 기존 데이터 호환성을 검증한다.
  evaluation_history·created_by는 추가 워크플로와 함께 검토하고 정본 설계로 자동 채택하지 않는다.
  사원·연도 1건과 평가 당시 조직 스냅샷은 기존 설계 기준을 유지한다.
- 인프라 영향: 0002는 실제 DDL을 포함한다. 코드 병합만으로 적용 승인된 것으로 해석하지 않는다.

## HR-01 · 개인정보 변경 요청 테이블의 이중 구조

- 담당: workforce, DB·문서 담당 협업.
- 기준: 공용 설계·테이블 명세는 employee_change_requests와 항목별 field_code·before_value·requested_value 구조.
- 현재 동작: [0004](../../backend/workforce/migrations/0004_personal_info_change_request.py)는
  personal_info_change_requests를 신규 생성하며 이메일·은행·계좌 전후 값을 별도 컬럼에 저장한다.
- 영향: 기존 테이블 사용 여부·데이터를 확인하지 않고 정본을 바꾸면 요청 이력이 분리될 수 있다.
  실제 유실·중복 여부는 미확인이다.
- 작업: 두 테이블의 존재·스키마·행 수·이용 경로를 읽기 전용으로 확인하고 기존 테이블 매핑 또는
  승인된 구조 전환안을 작성한다. 데이터의 실제 값은 보고서에 노출하지 않는다.
- 결정 요청: 정본 테이블·요청 단위, 기존 데이터 보존·전환 방향.
- 완료 기준: 기존 이력을 보존하고 승인·반려·취소·동시 요청을 검증한다.
  마이그레이션 계획·SQL·스키마 차이와 실제 적용 여부를 분리해 제출한다.
- 인프라 영향: DDL·데이터 전환은 환경과 권한 확인 및 별도 승인 후 진행.

## HR-02 · 급여계좌 보호와 개인정보 이력 보존

- 담당: workforce, 보안·문서 담당 협업.
- 기준: HR-003·HR-012,
  [BL-03](https://app.notion.com/p/3d78eced448d811bb8eafdb88c735b93)의 저장 암호화·조회 마스킹.
- 현재 동작: 완료 요청의 계좌는 일부 마스킹하지만 대기 요청값·현재 사원 계좌는 원문 저장이다.
  이력 보존·파기, 조회 감사로그는 기여 초안에 미구현으로 기록되어 있다.
- 작업: 원문 저장 경로·응답 권한을 조사하고 암호화·키 관리·마스킹·보존/파기안을 작성한다.
  마스킹된 완료 이력과 HR-003의 변경 전후 값 추적 요구를 함께 검토한다.
- 결정 요청: 이력별 최소 보존기간과 보호 방식, 승인 처리에 필요한 원문 조회 범위.
  감사로그는 기존 규칙의 직접 요구와 추가 제안을 구분한다.
- 완료 기준: 원문 계좌가 비허용 응답·로그·보고서에 노출되지 않는다.
  승인 기능과 이력 추적을 보존하고 암호화·복호화 권한·보존 종료 처리를 검증한다.
- 인프라 영향: 키·기존 데이터 전환은 별도 설계·승인 필요.

## HR-03 · 특별 승인선과 기타 추가 제한

- 담당: workforce, accounts·제품 담당 협업.
- 기준: HR-002·HR-003·HR-011, FN-HR-002~FN-HR-005·FN-HR-011.
- 현재 동작: HR 요청자는 HR인 소속 부서장만 처리하고, 요청자 자신이 부서장이면 본인 처리 가능,
  해당 처리자가 없으면 superuser만 처리한다. 내선번호 직접 수정 금지·대기 요청 1건 제한,
  사내 이메일 승인 시 로그인 이메일 동기화도 구현되어 있다.
- 작업: [기여 초안](../contributions/workforce/feature-workforce-employee-info/README.md)의
  추가 정책을 공용 명세와 분리하고 각각의 유지·수정 제안을 작성한다.
- 결정 요청: HR 본인 요청의 승인선·본인 승인, 연락처 범위, 요청 단위·중복 대기 허용,
  사내 이메일과 로그인 ID의 관계 및 계정 관리 경로에서의 일관성.
- 완료 기준: 일반 사원·HR·HR 부서장·superuser의 권한과 처리자 변경,
  이메일 중복·동시 요청·로그인 변경 성공/실패를 검증한다.
- 인프라 영향: 계정·사원 데이터 변경 경로 검토. 임의 데이터 수정 금지.

## PY-01 · 소수 입력과 최종 지급액 올림

- 담당: payroll, DB·제품 담당 협업.
- 기준: PY-003·PY-009, FN-PY-001. 소수 금액 발생 시 최종 지급액의 원 단위 미만을 올림한다.
- 현재 동작: [입력 검증](../../backend/payroll/presentation/serializers.py)은 소수 둘째 자리까지 허용하고,
  [계산](../../backend/payroll/domain/entities.py)은 지급 합계 - 공제 합계 그대로 반환한다.
  합성 입력 100.50은 입력 검증을 통과하고 계산 결과도 100.50이었다(DB 저장 검증 아님).
- 영향: 외화 입력이 없다는 설명만으로 소수 금액 경로의 불일치를 해소하지 못한다.
  DB의 net_pay = total_pay - total_deduct CHECK는 과거 기여 보고서에 기록된 값이며 이번에 재조회하지 않았다.
- 작업: 실제 CHECK를 읽기 전용 확인하고 합계 일관성과 최종 올림을 함께 만족하는 처리안을 작성한다.
  입력 단계 올림으로 명세를 임의 대체하지 않는다.
- 결정 요청: 소수 입력 지원 범위와 올림 차액을 합계·항목에 표현하는 방식.
- 완료 기준: 정수·소수 지급/공제 조합, 확정·정정·재확정의 계산과 이력,
  실제 제약 호환성을 검증하고 필요 마이그레이션 SQL·영향을 제출한다.
- 인프라 영향: 제약 변경·기존 금액 보정은 별도 승인 필요.

## PY-02 · 지급일·본인 처리·공개 범위 추가 정책

- 담당: payroll, 제품·문서 담당 협업.
- 기준: PY-001·PY-008 및
  [미확정 정책](https://app.notion.com/p/3d78eced448d81c0be0ff8f95b5ee9c3)의 정산일 미정.
- 현재 동작: 매월 25일·주말/등록 공휴일 전 평일 지급, 담당자 본인 급여 처리 금지,
  일반 사원의 확정 급여만 조회, 담당자만 이력 상세 조회를 구현했다.
- 작업: [기여 초안](../contributions/payroll/sylee/README.md)의 과거 담당자 결정을 새 제품 정책 제안으로 분리한다.
  이번 통합에서는 정산일 미정을 유지하고 추가 제한을 확정 규칙에 넣지 않는다.
- 결정 요청: 지급일·공휴일 운영, 담당자 자기거래 제한, 본인 공개 시점, 이력 공개 필드.
- 완료 기준: 결정 후 단일/복수 급여담당자, 일반 사원·타인 조회, 작성중·확정·확정취소,
  등록/미등록 휴일을 검증한다. 공휴일 데이터가 없는데 전체 공휴일을 지원한다고 표시하지 않는다.
- 인프라 영향: 공휴일·이력 데이터 수정이나 시드 삽입은 별도 승인 필요.

## OPS-01 · 현재 공유 DB 적용 여부와 배포 준비

- 담당: 각 모듈, 인프라 담당 협업.
- 근거: board 분류 시드 미적용, evaluation 0002·workforce 0004 미적용이 과거 기여 문서에 기록되어 있다.
  payroll의 일부 migration과 board 0002는 과거 적용 보고가 있다. 현재 상태는 이번에 확인하지 않았다.
- 작업: 적용 이력, 테이블·컬럼·제약, 필요한 마스터 존재를 읽기 전용 확인한다.
  경영담당자 Role 시드는 workforce migration에 없으므로 해당 역할 공급 경로도 확인한다.
  평가 사원·연도 중복과 상태·점수·등급의 기존 값 호환성을 집계 중심으로 점검한다.
- 결정 요청: 대상 환경·배포 순서·권한·마스터 운영 책임.
- 완료 기준: 코드 상태·migration 정의·실제 적용·실제 데이터 준비 여부를 각각 보고한다.
  SQLite에서 migration을 생략한 테스트 통과를 공유 PostgreSQL 스키마 검증으로 대체하지 않는다.
- 인프라 영향: 이 의제의 기본 작업은 읽기 전용. migrate·seed·데이터 변경은 별도 승인 필요.

## 검증·후속 기록

- 기존 테스트 5건 통과: 사원 목록 HR 권한, HR 부서장 평가 작성 거부, 제출 후 평가 확정,
  급여 차액 계산, 급여담당자 공지 작성. 테스트 통과는 현재 동작 확인이며 규칙 준수 인증이 아니다.
- 소수 금액은 합성 입력으로 serializer·도메인 계산만 확인했다.
- 브라우저 재현과 공유 DB·Redis 연결은 수행하지 않았다.
- 현재 문서 통합 후 Markdown 상대 링크·규칙 ID·diff 검증 결과는
  [통합 보고서](./2026-10-12_contribution-docs-integration.md)에 기록한다.
- 담당자 직접 전송·코드·DB 수정은 수행하지 않았다. Notion API·테이블의 충돌 없는 구현 정보만 부분 반영했으며
  이 문서의 의제는 정책 확정이나 해결 완료로 반영하지 않았다.
