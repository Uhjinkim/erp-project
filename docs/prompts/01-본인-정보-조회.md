상태: 완료 (2026-09-22)

## 사용한 프롬프트

```
workforce 앱에 FN-HR-001(본인 정보 조회) API를 구현해줘.

범위:
- 조회 주체: 로그인한 본인만 (다른 사원 조회 불가)
- 대상 데이터: Employee 1건 + 연관 Person(name, birth_date, gender),
  Department(dept_name), Position(position_name)

  본인 확인 후 노출 여부를 물어봐줘 — 미확정이면 제외하고 진행)

아키텍처:
- backend/workforce/application/에 read 전용 유스케이스(예: get_my_profile)를

- ORM 접근은 infrastructure/gateways.py의 기존 게이트웨이 패턴을 따르거나
  신규 read gateway 추가

  본인 employee_no만 조회하도록 제한 (다른 사원 번호 파라미터 받지 말 것)
- domain/에는 이번 기능으로 새 불변식이 없으면 손대지 않아도 됨

검증:
- backend/에서 uv run python manage.py check, ruff check ., pytest,
  makemigrations --check --dry-run
- 본인 것만 조회되고 타인 조회 시도는 403/404가 되는 테스트 추가

추적성:
- 테스트와 구현 대응표(workforce-implementation-map.md)에 FN-HR-001 명시
```

## 실제 구현 (프롬프트와 다르게 진행한 부분)

코드를 먼저 확인한 결과 `accounts/serializers.py`의 `CurrentUserSerializer`가 이미
`GET /api/auth/me/`로 로그인한 사원 본인의 `emp_no`/`name`/`dept_no`/`dept_name`/
`position_code`/`position_name`/`tenure_status`를 세션 식별용으로 반환하고 있었다.
새 엔드포인트를 따로 만들면 "본인 정보"를 보여주는 API가 두 개로 중복되므로,
기존 `get_employee()`에 나머지 개인정보 필드를 추가하는 쪽으로 범위를 좁혔다
(AGENTS.md의 "기존 동작을 보존하고 무관한 리팩터 지양" 원칙).

- 변경 파일: `backend/accounts/serializers.py`
  (`CurrentUserSerializer.get_employee`에 `birth_date`, `gender`, `email`,
  `phone`, `extension_no`, `address`, `bank_code`, `account_no`, `hire_date`,
  `term_date` 추가)
- `CurrentUserView`는 이미 `employee__person`/`department`/`position`을
  select_related 하고 있어 추가 쿼리 없이 반영됨
- 조회 주체는 여전히 `request.user` 세션 기준이라 별도 인가 로직 없이 "본인만
  조회 가능" 제약이 자연히 유지됨
- 테스트: `backend/tests/test_accounts_workforce.py::test_me_response_includes_own_profile_fields`
  추가, 새 필드가 `/api/auth/me/` 응답에 포함되는지 검증
- 구현 대응표(`docs/specs/notion/workforce-implementation-map.md`)에 FN-HR-001을
  "현재 구현"으로 이동하고 나머지(FN-HR-002~005, 011)는 "후속 구현"에 남김
- 계좌(`bank_code`, `account_no`) 필드는 본인 조회이므로 포함했다 — 급여계좌
  변경 요청(FN-HR-003)이 다음 단계에서 이 값을 참조해야 하기 때문

## 후속 리팩터: vacation처럼 모듈화 (2026-09-22)

1차 구현은 `accounts/serializers.py`가 `workforce`의 ORM 모델(`Employee`, `Person`)을
직접 조회해, `vacation` 앱이 지키던 "다른 앱은 `WorkforceQueryGateway` 포트로만 workforce를
조회한다"는 경계를 깨고 있었다. 사용자 요청으로 `vacation/`과 같은 방식으로 재구성했다.

- `backend/workforce/domain/policies.py`: `EmployeeProfile` frozen dataclass 추가
- `backend/workforce/application/ports.py`: `EmployeeProfileGateway` Protocol 추가
- `backend/workforce/application/services.py`: `get_employee_profile(employee_no, gateway)`
  유스케이스 추가
- `backend/workforce/infrastructure/gateways.py`:
  `DjangoWorkforceQueryGateway.employee_profile()` 구현 추가
- `backend/accounts/serializers.py`: `get_employee()`가 이제 ORM 대신
  `get_employee_profile()`만 호출
- `backend/accounts/views.py`: 더 이상 필요 없는 `employee__person/department/position`
  select_related를 `employee`로 단순화
- 신규 테스트: `test_get_employee_profile_reads_through_workforce_application_layer`,
  `test_get_employee_profile_returns_none_for_unknown_employee`
  (`backend/tests/test_accounts_workforce.py`)

전체 `pytest` 28 passed, `ruff check .`/`manage.py check`/`makemigrations --check --dry-run`
모두 통과. 자세한 내용과 이 리팩터 검증 과정에서 함께 고친 로컬 개발 환경 버그
(`start-dev.ps1`, `demo_settings.py`, `CSRF_TRUSTED_ORIGINS`)는
