## 1. 목적과 기준 자료

확정 디자인을 화면 단위로 분석한 뒤 기능 모듈별로 배정한다. 디자인시스템과 앱 공통 토대를 먼저
통합하고, 팀원은 정해진 공통 계약 위에서 자신의 모듈을 구현한다. 한 화면을 목록·폼·CSS 담당으로
잘게 나누기보다 같은 업무 흐름의 조회·입력·처리·이력을 한 담당 단위에 묶는다.

이번 문서는 계획과 후속 작업 지시의 기준이다. 디자인시스템, 라우팅, 모듈 디렉터리 생성과 기존
화면 전환은 후속 구현 단계에서 수행한다.

이번 작성에서 Notion 원문 재조회나 갱신은 수행하지 않았다.

## 2. 현재 구현에서 출발할 지점

현재 프론트는 React 19·TypeScript·Vite·Bun을 사용한다. 별도 라우터, UI 라이브러리,
컴포넌트 전시 도구, 프론트 테스트 러너는 현재 package.json에 없다.

- `App.tsx`에 인증 시작, 모듈 전환, health 조회와 휴가 업무가 함께 있다.
- 게시판·사원·평가·급여는 `components/*Panel.tsx`에 있으며 전역 `styles.css`를 함께 사용한다.
- 전송 계층은 `api/client.ts`, 모듈 API는 `api/*.ts`, 전송 타입은 `types/*.ts`에 있다.
- 휴가 API 호출과 타입은 아직 App 내부에 있다. 토대 담당자와 휴가 담당자가 이관 경계를 합의해야 한다.
- Graphite 시안은 정적 HTML·JS·CSS다. 갤러리 조작 코드와 예시 업무 데이터를 앱으로 복사하지 않는다.

토대 구축 때 기존 API 동작을 보존하면서 앱 조립과 업무 화면을 분리한다. 전역 CSS를 모두 한 번에
바꾸지 않고 새 공통 스타일과 기존 화면의 영향을 분리해 모듈별로 전환한다.

`frontend/src/` 기준의 **후속 구현 목표 경로**다.

팀원이 적으면 F0와 F8, F2와 F3 등을 한 사람이 맡을 수 있다. 이 경우에도 수정 경계와 작업 카드는
유지한다. 많은 팀원이 배정되더라도 같은 모듈의 API·타입 파일을 동시에 수정하게 나누지 않는다.

### 기존 파일 이관 규칙

1. F0가 기존 파일 → 새 소유자 → 새 경로 → 이관 PR을 적은 목록을 확정한다.
2. `api/workforce.ts`의 본인 조회·연락처·변경 요청 함수와 관련 타입은 F2로 분리한다.
   공용 `EmployeeDetail` 등 기존 타입은 F3가 유지하고 F2는 공개 타입을 참조한다. 복제하지 않는다.
3. F0가 휴가를 독립 진입 컴포넌트로 추출해 앱 조립 경계를 만든 뒤 F4에 넘긴다.
   기능 팀이 App 내부를 각자 수정하지 않는다.
4. 기존 Panel·EmployeeInfoCard·PersonalInfoRequests의 이동 또는 교체는 해당 모듈 소유자가 수행한다.
   F0는 이관 목록의 범위만 먼저 조정하며 기능 팀과 동시에 같은 파일을 옮기지 않는다.
5. F0의 계약·이관 PR이 dev에 병합된 커밋을 기능 배정의 시작 기준으로 기록한다.

## 5. 디자인시스템 포함 기준

컴포넌트는 다음 세 층으로 구분한다.

1. **디자인시스템**: 색·글자·간격·기본 UI와 업무에 무관한 반복 패턴. 업무 API와 역할을 알지 않는다.
2. **앱 공통**: 로그인 상태, 메뉴, 페이지 조립, 공통 오류·연결 상태. 디자인시스템을 사용하지만 업무 앱에 속한다.
3. **모듈 내부**: 업무 필드, 업무 상태, 처리 동선과 API 연결. 다른 모듈에서 직접 import하지 않는다.

기본 버튼·입력처럼 일관성이 필요한 요소는 처음부터 공용화한다. 복합 UI는 서로 다른 두 모듈에서
같은 동작·접근성·변형이 실제로 필요할 때 공용 후보가 된다. 이름·모양이 비슷하다는 이유만으로
업무 폼이나 승인 처리 전체를 범용화하지 않는다.

| 요소 | 디자인시스템 포함 | 공용 책임과 계약 | 모듈에 남길 내용·시점 |
| --- | --- | --- | --- |
| 색·글자·간격·경계·그림자·레이어 | 포함, P0 | 의미 기반 CSS 토큰, 사용 예시 | 업무별 원색·임의 z-index 재정의 금지 |

| FormField·FieldError | 포함, P0 | label·설명·필수·오류의 ID 연결 | 이메일 중복·계좌 정책은 서버/모듈 |
| Badge·Alert | 포함, P0 | `tone`과 문구를 전달받음, 색 외 텍스트 표시 | 휴가/평가/급여 상태 → tone 매핑은 각 모듈 |
| Spinner·Skeleton·EmptyState·ErrorState | 포함, P0 | 로딩/없음/실패의 표시와 재시도 callback | 401/403/503의 판단·재요청은 앱/모듈 |
| Card·Section·PageHeader·DetailList | 포함, P0 | 제목·설명·actions·내용 슬롯, 의미 있는 HTML | 사원 개인정보 항목과 업무 헤더 문구는 모듈 |
| Tabs | 포함, P0 | 선택 값·변경 callback·키보드 동작 | 라우트 링크는 앱, 목록 상태 필터는 모듈 |
| Modal·Drawer·ConfirmDialog | 포함, P0 | 제목, 열림 상태, 닫기, 크기, focus trap·복귀·Escape | 퇴사·반려·회수 사유와 실행은 모듈 |
| Table 기본 요소 | 포함, P0 | table/caption/th·정렬 버튼·가로 스크롤, 명시적 row key | 열 정의·행 작업·API 호출·업무 상태는 모듈 |
| Pagination | 조건부, P1 | 페이지/총수/변경 callback, 클라이언트·서버 모드 구분 | 현재 배열 응답을 서버 페이지네이션으로 가정하지 않음 |
| FilterBar·SearchField | 표시 골격 포함, P1 | children/초기화/검색 입력, 적용·즉시 반영 방식 명시 | 기간·부서·상태 필터의 의미·직렬화는 모듈 |
| Timeline·Stepper·MetricCard | 조건부, P1 | 검증된 두 소비 화면에서 공통 구조만 추출 | 이력 권한, 단계 전환·지표 집계는 모듈 |
| DataTable 전체 엔진 | 초기 제외 | 필수 열 렌더링·정렬 외 범용 엔진은 별도 검토 | 열 설정·내보내기·가상화가 확정되기 전 도입하지 않음 |
| Date/DateTime 입력 | 네이티브 래퍼 P0, 달력은 조건부 | label·값·오류, 날짜와 일시 구분 | 반차·차감·기간 중복은 휴가; 정산 기간은 급여 |
| 금액 표시·입력 | 초기 모듈 전용 | 숫자 표시가 실제 공유되면 포맷 함수만 추출 | 급여 합계·올림·공제 규칙은 서버 기준 |
| 사원 선택기 | 초기 제외 | 필요 시 최소 식별자·표시값만 받는 UI로 검토 | 평가/급여 대상은 업무별 전용 API·소유 모듈 |
| 승인 처리·전후 비교 폼 | 제외 | 공통 Alert/Dialog/DetailList 조합 | 개인정보·휴가·평가·급여 처리 규칙 각각 유지 |
| 게시글 폼·평가 폼·급여 항목표 | 제외 | 공통 입력·표를 사용 | 필드·상태·저장·합계 등 업무 내용은 모듈 |
| AppShell·메뉴·SessionProvider·접근 안내 | 제외, 앱 공통 | F0 소유, 디자인시스템을 소비 | 인증·역할·라우팅을 디자인시스템에 넣지 않음 |
| ConnectionStatus·API client | 제외, 앱 공통 | F0가 기존 구현을 이관·보존 | 전송 코드·health 로직을 UI 원자에 넣지 않음 |

P0는 기능 개발 시작에 필요한 최소 공통 범위이고, P1은 소비 화면을 확인한 후 추가한다. 시안의
내보내기·열 설정·읽지 않음·알림 버튼은 기능/API 계약이 없으면 작동하는 기능처럼 표시하지 않는다.

### 토큰과 디자인 검수

- 원시 팔레트와 의미 토큰을 나눈다. 예: `color-surface`, `color-text`, `color-border`,
  `color-action`, `color-danger`, `color-focus`, `space-*`, `font-*`, `layer-*`.
- Graphite의 어두운 상단·아이콘 레일, 밝은 메뉴·본문, 파란 주요 액션, 촘촘한 표 구조를 기준으로
  실제 화면용 토큰 표를 작성한다. 시안 CSS 값은 추출 근거이고 확정 토큰값은 토대 작업에서 기록한다.
- 갤러리는 축소 캔버스에 7~10px 글자를 사용한다. 앱 글자 크기를 그대로 복사하거나 앱에 16:10
  고정 비율·overflow hidden을 적용하지 않는다. 폰트 제공·라이선스와 실사용 크기를 먼저 확인한다.
- 기준 뷰포트, 긴 목록, 긴 이름·오류 문구, 브라우저 확대, 작은 화면에서 메뉴·표 스크롤을 검수한다.
  모바일 지원 범위와 메뉴 접힘 기준은 시안 분석 단계에서 기록하고 팀마다 다르게 정하지 않는다.
- 컴포넌트 전시에는 기본·hover·focus·disabled·pending·error 상태를 함께 둔다. 전시 화면은
  개발 전용이며 실제 사원·급여·계좌 데이터를 사용하지 않는다.

## 6. 구조와 공통 계약

목표 구조는 다음과 같다. 기존 API·전송 타입 경로를 유지하고 복잡한 UI만 기능별로 묶는다.

```text
frontend/src/
  app/                    # 앱 조립, 라우트·메뉴 등록, 세션·연결 상태
  components/
    ui/                   # 기본 UI
    patterns/             # 업무에 무관한 반복 조합
    layout/               # 앱 셸·내비게이션
  styles/                 # 토큰·reset·공통 기본 스타일
  api/                    # client, auth, profile, workforce, vacation 등
  types/                  # 서버 전송 DTO·공개 전송 타입
  features/<module>/
    index.ts              # 공개 진입점
    screens/              # 화면 조립
    components/           # 업무 UI
    hooks/                # 조회·변경·상태 관리
    *.module.css          # 모듈 지역 스타일
    fixtures/             # 필요한 경우 개발 전용 합성 응답
```

필요 없는 하위 폴더나 빈 컴포넌트는 미리 만들지 않는다. 업무용 화면 모델·타입은 feature 내부에
두며, 다른 모듈이 필요한 서버 DTO만 `types/`에서 공개한다.

### 기능 개발 시작 전 F0가 고정할 계약

| 계약 | 반드시 기록할 내용 | 경계 |
| --- | --- | --- |
| 화면 등록 | 모듈 ID, 화면 ID, URL 패턴, 메뉴 그룹·순서, label, 진입 컴포넌트, 접근 안내 방식 | 모듈별 등록 파일을 앱에서 조합; 중앙 메뉴 파일은 F0만 변경 |
| 페이지 조립 | title·description·actions 슬롯, 본문 너비·스크롤 책임 | 기능 화면은 셸·상단·아이콘 레일을 다시 만들지 않음 |
| 세션 | 확인 중/로그인/비로그인, `CurrentUser`, 로그아웃·만료 통지, 복귀 URL | 토큰을 별도 저장하지 않고 서버 세션·CSRF 유지 |
| 연결·오류 | 공통 표시, 재시도, 업무별 요청 가능 상태, 401/403/5xx 처리 | health 결과만으로 모든 업무의 권한·가용성을 보증하지 않음 |
| UI 공개 API | props·변형·접근성·스타일 확장 범위·예시 | 승인용 전용 prop를 기본 Button에 계속 추가하지 않음 |
| 모듈 데이터 | 요청 함수·DTO·오류·조회 범위·fixture 예시 | 화면 간 조회가 필요하면 공개 계약으로 연결; 내부 hook import 금지 |
| 스타일 | CSS Modules 사용, 토큰 이름, 공통 CSS import 순서 | 전역 element/범용 class 선택자를 feature CSS에 추가하지 않음 |
| 도구 | 라우팅 방식·라이브러리, 전시 방식, 회귀 검증 도구, 의존성 관리 담당 | package.json·bun.lock은 F0가 Bun으로 갱신 |

라우팅은 직접 URL 열기·새로고침·뒤로가기·화면 간 복귀를 지원해야 한다. 현재 모듈 useState
전환을 여러 팀이 개별 확장하지 않는다. 라우터·UI·아이콘·테스트 도구를 새로 도입할 경우 근거와
범위를 토대 기여 문서에 기록하고 실제 설치 시 공식 문서를 확인한다.

공통 계약 변경 요청에는 소비 모듈, 시안 화면 ID, 현재 계약의 한계, 제안 props, 다른 모듈 영향,
검증 예시를 적는다. F0가 공통 PR을 먼저 통합하고 소비자가 이를 받아 작업한다. 요청 대기 중에는
독립 업무 로직·fixture·화면 분석을 진행할 수 있지만 같은 공용 UI의 복제품을 만들지 않는다.

### 인증·오류 주의점

현재 API는 미인증·권한 부족·CSRF 오류에 모두 403을 반환할 수 있다. 모든 403을 로그아웃으로
처리하면 정상 로그인한 사용자의 권한 오류도 세션 만료로 보인다. F0는 `/api/auth/me/`의 세션
확인과 업무 API의 접근 실패를 구분하는 흐름을 정하고, 확인 API 장애를 만료로 단정하지 않는다.
로그아웃·만료·사용자 전환 시 이전 사용자의 목록·상세·급여 등 화면 상태와 캐시를 비운다.

`api/client.ts`의 타임아웃·CSRF·쿠키 처리를 사용한다. 파일 다운로드처럼 다른 응답이 필요한
경우에도 인증·CSRF 기준을 일관되게 유지한다. 필드 오류 구조를 보존할 개선이 필요하면 F0의
별도 공통 변경으로 수행한다. 기능 화면마다 fetch 래퍼를 새로 만들지 않는다.

## 7. 작업 순서와 시작·완료 조건

| 단계 | 작업 | 산출물 | 다음 단계 시작 조건 |
| --- | --- | --- | --- |
| A 디자인·범위 분석 | 확정 시안 버전과 39개 화면 대조, 역할·API·상태·반응형 분석 | 화면 목록, 컴포넌트 후보, 미확정 항목, 담당표 | 디자인 기준·모듈 경계·작업 범위가 기록됨 |
| B 공통 계약 설계 | 공용 포함표·props·토큰·라우트·인증·이관 경계 확정 | 계약 문서와 모듈 배정 카드 초안 | 같은 파일·같은 컴포넌트 중복 소유가 없음 |
| C 공통 토대 구현 | P0 UI·전시·셸·인증·연결·화면 등록, 기존 기능 진입점 분리 | 공통 PR, 예시 화면, 검증 기록 | 아래 토대 완료 기준 충족 후 dev 병합 |
| D 대표 흐름 검증 | 휴가의 목록→입력→상세→사유 처리로 계약 확인 | 합성 응답 기반 화면과 수정된 계약 | feature 코드 복사 없이 공통 UI로 구성 가능 |
| E 모듈 병렬 구현 | 각 기능의 목록·상세·폼·처리·이력과 API 연결 | 모듈 PR, 기여 문서, 화면 검수 자료 | 통합 기준 커밋과 동일한 공통 계약 사용 |
| F 통합 검수 | 직접 URL·새로고침·복수 역할·만료·오류·디자인·회귀 검수 | 통합 검증 기록·남은 의제 | 승인 범위 동작, 미완료 항목 명시 |

단계 A·B 중에도 팀원은 API 조사와 업무 UI 설계를 진행할 수 있다. 공용 파일 변경이 필요한
본격 화면 개발은 C·D 이후 시작한다. 일정·실명은 화면 복잡도와 인원 확인 후 작업 카드에 적는다.

### 공통 토대 완료 기준

- 토큰과 P0 컴포넌트의 공개 props·예시·접근성 규칙이 있다.
- 긴 본문·표에서 셸 스크롤이 동작하고, 키보드로 메뉴·탭·dialog를 사용할 수 있다.
- 로그인·로그아웃·만료·권한 없음·연결 실패가 구분되며 개발용 사용자 전환은 운영 UI에 노출되지 않는다.
- 모듈 진입점과 화면 등록 예시가 있으며 빈 화면은 “준비 중”으로 표시한다. 미구현 기능에 가짜 성공을 주지 않는다.
- 휴가 대표 흐름에서 공통 UI 계약을 확인하고 기존 기능 회귀를 점검했다.
- API·타입 이관과 전역 스타일 경계가 정리되어 팀원이 App·공통 client·전역 CSS를 동시에 수정하지 않는다.
- `bun run lint`, `bun run build`가 통과하고 시작 기준 커밋·계약 변경 방식·미해결 사항을 기록했다.

## 8. 팀원에게 전달할 작업 안내 양식

아래 카드와 4절의 해당 모듈 행을 함께 전달한다. 카드가 확정되면 팀원은 추가 공통 설계 없이
바로 착수할 수 있어야 한다.

```markdown
### F<번호> · <모듈명> 프론트 작업

- 담당자 / 리뷰어:
- 시작 기준: dev 커밋, 공통 토대 PR, 계약 버전
- 브랜치: feature/<module>-ui-<topic>
- 디자인: 확정 시안 경로/링크, 버전·확정일, 화면 ID
- 업무 근거: FN/규칙 ID, API 명세, 관련 미해결 의제
- 화면 범위: 목록 / 상세 / 생성·수정 / 처리 / 이력 / 추가 상태
- 전용 수정 경로: feature, API, 타입, 기존 파일 이관 대상
- 공용 소비: 컴포넌트 이름·변형·참조 예시
- 외부 계약: 요청/응답·권한·오류·필터·정렬·페이지 처리 방식
- UI 상태: loading / empty / error / forbidden / expired / pending / success
- 의존 작업: 선행 PR, 다른 모듈 공개 계약, 결정 대기 항목
- 이번에 구현하지 않을 기능: 사유와 후속 의제
- 단계별 제출: 화면·fixture → API 연결 → 회귀·디자인 검수
- 완료 기준: 아래 모듈 완료 기준 + 이 모듈의 특수 조건
- 검증: lint/build, 업무 시나리오, 사용한 합성 데이터·환경
- 문서: docs/contributions/<module>/<branch-slug>/README.md
- 일정 / 남은 질문 / 공용 변경 요청:
```

### 모듈별 지시 시 추가할 항목

- **F1 홈**: 각 카드의 공급 API·갱신 시점·실패 처리와 이동 대상 지정. 특정 카드 조회가 실패해도
  다른 카드가 사라지지 않게 한다. 잔여일수·읽지 않은 공지·팀 일정 수치를 fixture로 출시하지 않는다.
- **F2 내 정보**: 연락처·주소·이메일·급여계좌를 수정 요청으로 제출하고 취소·승인·반려 후 다시 조회한다.
  기본 목록·완료 이력은 계좌를 마스킹한다. HR-01~03 결정 대기 범위를 카드에 적는다.
- **F3 사원·조직**: 일반 사원과 HR 관리자의 조회 범위를 구분한다. 퇴사·재입사·발령은 서버의
  전용 처리 계약을 확인하며 프론트의 여러 PATCH로 업무 트랜잭션을 대체하지 않는다.
- **F4 휴가**: 신청 폼을 신규·재신청 모드에서 재사용하고 처리 버튼은 pending 중 중복 실행을 막는다.
  상세는 현재 목록·history API 등 이용 가능한 계약으로 구성하며 존재하지 않는 상세 API를 가정하지 않는다.
  날짜/일시·시간대·차감일수는 전송 형식과 표시 형식을 분리한다.
- **F5 게시판**: 작성·수정 폼은 모듈 내부에서 재사용한다. 공지 분류·복수 역할 선택은 BD-01 결정에
  따른다. 댓글·대댓글·읽음 표시는 BD-02 등 승인 범위가 확정되기 전 필수 구현으로 배정하지 않는다.
- **F6 평가**: 팀 대상 조회와 본인 결과 조회를 분리한다. 승인된 기본 흐름과 현재 코드의 제출·반려·
  재배정·제외 등을 구분하고 EV-01·02 결정 결과를 카드에 적는다.
- **F7 급여**: 급여 대상 조회는 `api/payroll.ts`의 업무 전용 계약부터 확인한다. 금액·합계·올림은
  서버 결과를 기준으로 표시하며 정산일을 25일 등으로 임의 확정하지 않는다. 기존 명세서 저장 동작도 회귀 검수한다.
- **F8 시스템**: 사원 역할 편집은 F3의 화면으로 연결한다. 시스템관리자 역할과 HR/슈퍼유저 API
  권한의 관계를 먼저 확인하고 health 상세에는 비밀값·내부 주소·예외 원문을 노출하지 않는다.

기존 의제 INT-01은 과거 조사 결과이므로 착수 시 현재 코드로 재확인한다. 평가에는 팀 대상,
급여에는 급여 대상 클라이언트 함수가 이미 존재한다. 함수 존재만으로 권한·연동 의제가 해결되었다고
판정하지 않고 실제 호출 경로와 역할별 성공·실패를 검증한다.

## 9. 중복·충돌 방지 운영 규칙

1. 공용 경로·진입점·의존성 파일은 F0만 수정한다. 모듈별 등록 파일은 각 팀이 만들고 앱 조립 변경은
   F0의 별도 PR로 처리한다. CODEOWNERS 등 자동 보호를 도입한다면 실제 팀 계정 확정 후 설정한다.
2. feature A는 feature B의 screens/components/hooks를 import하지 않는다. 공유 DTO·공개 데이터
   계약을 참조하며 업무 화면 간 연결은 화면 등록의 이동 계약을 사용한다.
3. 모듈은 CSS Modules와 공통 토큰을 사용한다. `.card`, `.button`, `button`, `table` 같은 전역
   스타일 재정의와 공용 컴포넌트 내부 DOM 선택자에 의존하는 덮어쓰기를 금지한다.
4. 공용 복합 컴포넌트 제안은 두 소비 사례·공통 동작·업무별 차이·공개 props를 검토한다.
   승격 전까지 모듈 내부에 둔다. 과도한 공용화와 기본 UI의 복제를 함께 막는다.
5. backend 권한을 프론트 Role 문자열·부서명만으로 재정의하지 않는다. 복수 역할은 독립 권한을
   고려하고 직접 URL/API 실패도 처리한다. 공통 UI는 업무별 역할을 판단하지 않는다.
6. 기본 공통 흐름을 먼저 병합하고 기능 PR은 모듈별로 검토한다. 공통 변경과 여러 모듈 변경을
   한 PR에 계속 묶지 않는다. 이관·공통·기능 변경은 선후 관계를 기록한다.

## 10. 브랜치·검증·완료 기준

최신 dev에서 기능 브랜치를 시작하고 기존 [협업 절차](./module-branch-docs-workflow.md)에 따라
기여 초안을 생성한다. F0는 `frontend` 모듈, F1은 `home`, F2는 `profile`, F3~F8은
`workforce`·`vacation`·`board`·`evaluation`·`payroll`·`system`을 기여 폴더 이름으로 사용한다.
기능 팀은 이 안내서를 직접 수정하지 않고 변경 제안을 자신의 기여 초안에 적는다.

프론트 검증 명령은 frontend 디렉터리에서 실행한다.

```bash
bun run lint
bun run build
```

모듈 완료 시 다음 항목을 확인한다.

- 배정된 화면 ID와 관련 FN/규칙 ID를 PR에 연결했다.
- 기본·빈 목록·로딩·필드 오류·업무 오류·권한 없음·만료·서버 연결 실패·처리 중 상태를 검수했다.
- 일반 사원, 해당 관리자, 복수 역할, 비허용 역할을 합성 응답으로 검증했다.
- 직접 URL·새로고침·뒤로가기·목록 복귀, 조회 중 화면 전환과 로그아웃 후 데이터 제거를 확인했다.
- 수정 성공/실패·연속 클릭·서버 거부 후 UI 복원·최신 응답 재조회를 확인했다.
- 키보드·label·focus·dialog 복귀·색 외 상태 표현·긴 데이터·뷰포트 변경을 확인했다.
- 목록 API의 필터·정렬·페이지 지원과 클라이언트 처리를 구분했다. 현재 배열 응답에 가짜 서버 페이지 API를 만들지 않았다.
- 새 UI와 기존 모듈 전환·인증·명세서 저장 등 영향을 받는 기능의 회귀를 확인했다.
- lint/build 결과, 디자인 비교 자료, 미검증 범위, 공용 계약 변경과 미해결 의제를 기여 초안에 기록했다.
- diff/status를 확인하고 타인 변경을 보존했다. 최신 origin/dev를 받아 작업을 커밋한 후
  `docs-workflow.sh check` 또는 PowerShell의 동등 명령으로 문서 범위를 검사했다.

공통 토대와 주요 변경에는 의미 있는 회귀 검증을 추가한다. 현재 프론트 테스트 러너가 없으므로
토대 단계에서 도구와 범위를 정한다. 도입 전에는 수동 검증 시나리오·합성 응답·실제 실행 결과를
기록하며 수동 확인을 자동 테스트 통과로 표현하지 않는다.

일반 통합 실행은 저장소의 start-dev 스크립트와 nginx 진입점을 따른다. UI 전용·집중 검증에는
Vite와 합성 응답을 사용할 수 있다. 공유 DB·Redis를 테스트 준비용으로 migration·seed·수정하지
않는다. 실제 API 연결 검증은 대상·권한을 확인하고 읽기 전용으로 시작하며 업무 데이터 쓰기는
명시적인 대상 환경·권한 승인 후 수행한다.

## 구현 통합 현황 · 2026-10-28 갱신

이 안내서의 Graphite 화면 분할은 초기 배정 기준이다. 현재 코드에서 profile 4개, workforce 7개,
휴가 7개, 게시판 3개, 평가 4개, 급여 5개 업무 화면을 모듈 공개 진입점으로 연결했다.
게시판은 2026-10-14 기여 기록과 registration에 따라 공지·일반·작성 메뉴로 나뉘며 글 보기는
목록의 postId 상태다. 이전 board-detail/notice-write를 독립 메뉴의 미구현 과제로 다시 배정하지 않는다.

담당자의 후속 작업은 화면 분리 자체보다 실제 API/권한·브라우저·시안 검증과 미결 의제 처리다.
현재 진입점·필터/query·페이지 방식은 [공용 연결 계약 2절](./frontend-foundation-contracts.md),
유지·변경·충돌 분류는 [통합 보고서](../reports/2026-10-14_contribution-docs-integration.md),
미결 작업은 [최신 의제](../reports/2026-10-14_module-review-agenda.md)를 사용한다.
공통 Modal backdrop prop·unused legacy CSS 삭제 제안은 아직 적용하지 않았으므로 담당 모듈이
임의로 공용 계약을 변경하지 않는다. 제품 정책과 시안 검증의 완료 여부를 화면 연결 상태와 구분한다.
